# Modder task

The only objective verdict in the suite. No grader agent: the mod either lints
and loads, or it does not.

`modder` is a **pass/fail regression guard, not a delta**. The modding surface
is the wiki plus the RON format, and this epic changes neither. Its job is to
prove the epic did not break the external contract. A baseline FAIL is a wiki
bug, not a structure finding - fix it and rerun the baseline.

No repo. No `crates/`. No `.rs`. No `tasks/`. Not by instruction - those files
are not in the image, and the repository is never mounted.

## Brief

The paper handed to the agent is `papers/tier3-modder.md`, generated by
`make-papers.py` from `papers/src/tier3.md`. Reproduced here so the rationale
below sits next to what it explains:

> You are writing a mod for Nova Protocol, a 3D space shooter. Mods are RON
> data files - no Rust, no engine changes.
>
> Everything you need is in this directory: four wiki pages under `wiki/`, and
> two complete worked mods under `webmods/`.
>
> Build a mod called **Salvage Run** in a new folder `salvage-run/`:
>
> 1. A **bundle manifest** naming the mod, its author, a version, a
>    description, and `base` as its only dependency.
> 2. One **content file** holding two things:
>    - a **section prototype**: a variant of a base hull section with different
>      stats and a different id, so it is a new section rather than an override
>      of a base one;
>    - one **scenario** that uses it.
> 3. The scenario must, at minimum:
>    - spawn a player ship built from your new section plus base sections;
>    - light the scene (a scenario that authors no light renders black);
>    - spawn at least two non-player objects;
>    - declare a **sensor area** and react to a ship entering it;
>    - track at least one **scenario variable**, and gate at least one handler
>      on its value with a **filter**;
>    - show at least one **HUD objective** and complete it;
>    - declare a win **outcome** and a lose outcome.
>
> Keep it small. Roughly 150-250 lines of RON is the target - `gauntlet` is
> 1,122 lines and is far more than you need. Correctness beats scope.
>
> Write a short `salvage-run/README.md` saying what the mod does.
>
> Also write `GAPS.md`: every point where the wiki did not tell you something
> you needed, what you had to guess, and how you resolved it. Be specific -
> name the page and what was missing. This file is as valuable as the mod.
>
> Record your tool-call count at the end of `GAPS.md`.

## Why this shape

The brief is sized against the two worked examples. Everything it asks for is
demonstrated in `gauntlet` (a single scenario with areas, variables, filters,
objectives and both outcomes) and `the-ledger` (a multi-file campaign,
section-prototype overlays, cross-file references), so it is buildable from the
sandbox alone.

It is deliberately more than one RON construct:

| Construct | Why it is in the brief |
| --- | --- |
| Bundle manifest + `meta` + `dependencies` | the packaging half; a mod that lints but has no manifest is not a mod |
| `Section(( .. ))` content item | the content file is a `Vec<Content>` with a KIND flag; a scenario-only mod never exercises the other arm |
| `Scenario(( .. ))` content item | the main event |
| `dep://base/...` and `self://...` asset refs | the two reference schemes, and the pair the lint checks hardest |
| Areas + `OnEnter` | the only event with spatial setup, and the construct `gauntlet`'s own comments call out as easy to get wrong |
| Variables + filters | the gating vocabulary; a handler list with no filters is the trivial case |
| Objectives + outcomes | the player-visible half; a scenario with no outcome never ends |

`the-ledger`'s campaign structure is deliberately **out** of scope: it needs six
files and a campaign content item, which triples the size for no extra
construct coverage.

## Verdict

Copy `results/<run>/modder/tier3/salvage-run/` back into the repo and run, from
the repo root:

```sh
nix develop --command cargo run -p nova_assets --bin content -- lint <path>
```

Then load the scenario in-game and confirm it reaches Playing.

| Result | Verdict |
| --- | --- |
| lints clean AND loads AND reaches the win outcome | PASS |
| lints clean AND loads, outcome unreachable | PASS with note - the brief did not require a winnable route |
| lints clean, fails to load | FAIL |
| lint failure | FAIL |

Record it in `results/<run>/modder/tier3/verdict.json`, which `aggregate.py`
reads into the report:

```json
{
  "verdict": "PASS | PASS with note | FAIL",
  "lint_output": "the lint output verbatim",
  "notes": "anything the table above does not cover"
}
```

The tool-call count comes from the transcript and `GAPS.md` is already in the
result directory; neither needs transcribing.

**Every lint failure is a wiki bug.** The mod was built from the wiki alone; if
the wiki was sufficient, the lint passes. Open a task for each one regardless of
what this epic decides - they are real doc defects and they are the cheapest
findings in the whole benchmark.

Same rule for `GAPS.md`: each entry is a candidate doc fix, independent of the
refactor. Triage them separately from the tier 1 and tier 2 results so a
structure finding and a doc finding do not get confused.
