# Tier 2 - design

Three cross-cutting change requests. Run against the current tree (**baseline**)
and again after the epic (**after**), by the same personas as tier 1 except
`modder`.

Each agent produces a `NOTES.md`. **No code.** A reviewer agent grades it
against the rubric below, and must justify every score with a citation from the
agent's own NOTES.md.

**This file is the answer key.** It is mounted into the grader's container and
must never reach a respondent. The prompts they see are
`papers/tier2{a,b,c}-<persona>.md`, generated by `make-papers.py` from the task
bodies in `papers/src/`; the `### Prompt` blocks below are copies, kept here so
the ground truth sits next to the question it answers.

Owner ratifies these prompts and the ground-truth surface lists before the
baseline runs.

## Rubric

Reproduced from `README.md`. Each dimension is one number in `[0.00, 1.00]`,
two decimals - the same scale tier 1 uses. The grader must justify every score
with a citation.

| Dimension | Asks |
| --- | --- |
| Ownership | Does it name the right crates/modules to touch? |
| Completeness | Does it miss a required surface (prelude export, RON regeneration, wiki, CHANGELOG)? |
| No phantom structure | Does it invent modules that do not exist, or trust a misleading name? |
| Cost of arrival | Tool calls to a correct model |

"No phantom structure" is the dimension that catches names lying about their
contents - `hud/` holding a terminal runtime, `nova_modding` holding neither
bundle merge nor the portal client.

Anchors for the four dimensions. They are anchors, not buckets: score between
them where the note sits between them, and say in the citation which way you
judged it.

| Score | Ownership | Completeness | No phantom structure | Cost of arrival |
| --- | --- | --- | --- | --- |
| 1.00 | every required crate named, none spurious | every required surface named | nothing invented, no misleading name trusted | at or below the owner's count |
| 0.67 | one required crate missed | one required surface missed | one hedge or soft misread, self-flagged | within 2x the owner's count |
| 0.33 | two missed, or a wrong crate named as primary | two or three missed | one invented module or one name taken at face value | within 4x |
| 0.00 | the primary owner is wrong | four or more missed | the plan is built on structure that does not exist | above 4x, or gave up |

Completeness has a Required list to count against, so prefer the fraction of
required surfaces named over the anchor row when the two disagree. Cost of
arrival is a ratio against the owner's count, so interpolate it rather than
rounding to an anchor.

**Cost of arrival is null when there is no owner count.** The owner has no
container and no transcript, and works in an editor rather than a tool loop, so
for most tasks the denominator this dimension is defined as does not exist and
never will. When `/grade/owner-tool-calls.txt` reads `not recorded`, write
`null` and say so in the citation. Do **not** substitute an absolute judgement
of the respondent's count, and do not fall back on the 0.67 anchor as a
"neutral default" - both were done in the baseline, inconsistently, across
eleven of twelve cells, which put a quarter of every tier 2 headline on a
number nobody measured. The headline is then the mean of the dimensions that
were scored. The raw tool-call count is reported beside the score regardless;
it is the honest form of this metric and it needs no rubric.

Report per persona: four scores, the tool-call count, and the reviewer's
citations. The headline number is the mean of the four, also `0.00` to `1.00`.

## Ground-truth surface lists

These are the answer keys. They are what the reviewer scores Completeness
against. Every path was re-opened against the tree at HEAD `89c049fd` on
2026-08-07, after L0 landed.

Each list separates:

- **Required** - a correct plan must name it.
- **Credit** - naming it is evidence of a good model; missing it is not a
  Completeness deduction.

An agent that names a file NOT on either list is not automatically wrong -
the reviewer judges whether it is defensible. Inventing a path that does not
exist is a phantom-structure deduction regardless.

## Channel scope

A Required surface only counts against a persona that had some way to learn the
surface exists. `blind`'s image has every `.md` deleted and `rustdoc`'s holds
the rendered crate API and nothing else, so both were being marked down on
Completeness for not naming `CHANGELOG.md` and `web/src/wiki/**` - files
physically absent from their containers. That measures the sandbox, not the
codebase.

This is the tier 2 form of what `grade.sh` already does for tier 1, where the
key is filtered to the questions the persona was actually asked.

| Persona | Out of channel |
| --- | --- |
| `blind` | every `*.md` row - `CHANGELOG.md`, `web/src/wiki/**`. Nothing else; source, `Cargo.toml` and `assets/**` are all present |
| `rustdoc` | every row outside the rendered crate API - `*.md`, `web/**`, `assets/**`, `examples/**`, `Cargo.toml` |
| `tree` | none. `TREE.txt` lists every filename, so every Required path is nameable |
| `docs` | none. `CHANGELOG.md` is not staged, but `AGENTS.md`'s Documentation table names it, so the surface is knowable |
| `owner` | none |

Out-of-channel surfaces leave the Completeness denominator. They are reported
under `out_of_channel`, never `missed_required`, so a channel gap stays
readable as a channel gap.

## Task 1 - add a new ship section type

### Prompt

> Nova Protocol ships have modular sections: hull, thruster, controller,
> turret, torpedo. Plan the addition of a **new section type** - a "shield
> section" that projects a damage-absorbing bubble around the ship while it has
> power, is toggled by a player keybind, and shows its remaining charge on the
> HUD.
>
> You do not need to design the physics. You need to identify every part of the
> codebase that has to change, and say what each change is.

### Required surfaces

| Path | What changes |
| --- | --- |
| `crates/nova_gameplay/src/sections/base_section.rs:270` | new `SectionKind` variant; the doc at `:265-266` already states the three-part rule (variant + config module + plugin) |
| `crates/nova_gameplay/src/sections/` | new `shield_section` module (behaviour, config struct, plugin) |
| `crates/nova_gameplay/src/sections/mod.rs:6-14` | module declaration; `:17-25` prelude re-export; `:133-149` plugin registration inside `SpaceshipSectionPlugin` |
| `crates/nova_gameplay/src/input/` | the toggle intent - player input lives under `input/player/`, and `input/mod.rs` is the one plugin/one set model in the crate |
| `crates/nova_gameplay/src/hud/` | the charge readout, a new sibling of `ammo_readout.rs` / `flight_status.rs` |
| `crates/nova_assets/src/sections.rs:173` | `build_sections` - the authored stats for the stock shield section |
| `assets/base/**/*.content.ron` | regenerated by `cargo run -p nova_authoring --bin content -- gen`. **Never hand-edited** |
| `crates/nova_scenario/src/lint/ship.rs` | the ship lint matches on `SectionKind` |
| `crates/nova_editor/src/placement.rs`, `crates/nova_editor/src/ui/card.rs` | the editor palette matches on `SectionKind` |
| `CHANGELOG.md` | user-visible behavior, per `AGENTS.md`'s Documentation table |
| `web/src/wiki/dev/sections.md`, `web/src/wiki/dev/guide-add-section.md` | internals doc; the add-a-section guide is the surface this task literally follows |

### Credit

| Path | Why |
| --- | --- |
| `crates/nova_assets/src/balance.rs`, `merge.rs`, `mod_refs.rs` | all match on `SectionKind` |
| `crates/nova_scenario/src/lint/mod.rs`, `loader/mod.rs`, `objects/modification.rs`, `objects/spaceship.rs` | same |
| `crates/nova_probe/src/fixtures.rs` | matches on `SectionKind`, and is misplaced (see tier 1 `t1-013`) |
| `examples/sections/` | the per-section example convention |
| the affected player wiki + tutorial | required by the Documentation table only if first-flight changes |

### Why this task discriminates

`SectionKind` is matched in **27 files: 23 across 5 crates, plus 4 examples**.
Adding a variant is a non-exhaustive-match cascade, and nothing in the folder
structure discloses its reach. The plan's Completeness score is a direct measure of how far a reader
can see from `sections/`.

Second signal: the split between `nova_gameplay/src/sections/` (behaviour) and
`nova_assets/src/sections.rs` (authored data) is a name collision. An agent that
names only one has the content pipeline wrong.

## Task 2 - add a NOVA OS app

### Prompt

> The in-game NOVA OS terminal can launch apps - today `map` and the ship
> viewer. Plan the addition of a **new app**: a "cargo manifest" app, launched
> by typing `cargo` at the NOVA OS prompt, that lists the player ship's
> sections and their status, with its own key handling and its own brightness
> behaviour honouring the monitor settings.
>
> You do not need to design the visuals. You need to identify every part of the
> codebase that has to change, and say what each change is.

### Required surfaces

| Path | What changes |
| --- | --- |
| `crates/nova_os/src/app.rs:39` | implement the `NovaOsAppRuntime` trait; `:54` `spawn_body` is the view seam |
| `crates/nova_os/src/command.rs:86` | `TerminalCommand::app(name, summary, runtime)` - how a launch word is declared |
| `crates/nova_gameplay/src/hud/` | the new app's UI module, a sibling of `nova_os_map/` and `nova_os_ship/` - **not** in `nova_os` |
| `crates/nova_gameplay/src/hud/nova_os_map/mod.rs:98` or `nova_os_ship/mod.rs:109` | the registration pattern to copy: `.register(<command tree>)` into `NovaOsCommandRegistry` |
| `crates/nova_gameplay/src/hud/nova_os/mod.rs:121` | where `NovaOsCommandRegistry` is `init_resource`d |
| `crates/nova_gameplay/src/hud/nova_os/components.rs:132` | `NovaOsMonitorSettings` - the brightness/scan/sound state the app must honour |
| `crates/nova_menu/src/lib.rs:109`, `settings_store.rs:86` | that resource is registered and persisted by **nova_menu**, not by the crate that declares it |
| `crates/nova_gameplay/src/hud/nova_os/content.rs` | the shell's command list, summaries and breadcrumb text |
| `web/src/wiki/` | the player-facing NOVA OS page; `CHANGELOG.md` for the new command |

### Credit

| Path | Why |
| --- | --- |
| `crates/nova_gameplay/src/hud/nova_os_pointer_rig.rs` | shared pointer plumbing if the app is pickable |
| `crates/nova_gameplay/src/hud/nova_os/shell.rs:185` | where the app entity is named and spawned |
| `crates/nova_gameplay/src/hud/nova_os_map/scene.rs` / `nova_os_ship/scene.rs` | the pair to copy from if the app is 3D - and noting that they are near-duplicates |
| a `SystemSet` for the new app | noting that `NovaOsShipSystems` (`nova_os_ship/mod.rs:166`) and `NovaOsMapSystems` (`nova_os_map/mod.rs:139`) exist but are never passed to `configure_sets`, so copying them adds no ordering |
| `crates/nova_menu/src/pause.rs:51-54` | the `PauseStates::NovaOs` special case |

### Why this task discriminates

Three crates, and the boundary between them is a rule (`nova_os` owns no UI)
that is honored but written down only in `AGENTS.md`. An agent that puts the
app's UI in `nova_os` has broken the one clean boundary in the feature; an
agent that puts the settings in `nova_gameplay` has missed that `nova_menu`
owns the state.

The registry registration is the specific test: it is not in `nova_os`, and it
is not in `nova_os/mod.rs`. It is done twice, by each app's own module.

## Task 3 - add a new scenario action and event

### Prompt

> Scenario RON files declare handlers: an event fires, and a list of actions
> runs. Plan the addition of a **new event and a new action**:
>
> - a new event `OnDocked`, fired when a player ship comes to rest inside a
>   scenario area tagged as a dock;
> - a new action `SetHullRepairRate`, which changes how fast a scoped ship's
>   hull sections regenerate.
>
> You do not need to design the repair mechanic. You need to identify every part
> of the codebase that has to change, and say what each change is.

### Required surfaces

| Path | What changes |
| --- | --- |
| `crates/nova_events/src/lib.rs` | the new event kind joins the shared vocabulary; the crate doc at `:1-9` states exactly what belongs here |
| `crates/nova_events/src/engine.rs` | the queue/dispatch path the new kind flows through |
| `crates/nova_scenario/src/events.rs:16` | `EventConfig` - the RON `name` an author writes, mapped to the concrete `nova_events` type |
| `crates/nova_scenario/src/actions/mod.rs:42` | `EventActionConfig` - new variant; `:92` the `match` in `impl EventAction` |
| `crates/nova_scenario/src/actions/ship.rs` | where a ship-scoped action config and its `action()` belong |
| `crates/nova_scenario/src/actions/mod.rs:22` | prelude re-export |
| `crates/nova_gameplay/` | the **emitter** for `OnDocked` - gameplay detects the condition and emits; scenario only reacts. The area machinery is `CreateScenarioArea` / `OnEnter` / `OnExit` |
| `crates/nova_scenario/src/lint/scenario.rs` | the scenario lint validates handler names and action configs |
| `web/src/wiki/dev/modding-ron.md`, `web/src/wiki/dev/scenario-system.md`, `web/src/wiki/dev/guide-extend-scenarios.md` | format change; mark `(breaking)` if it breaks existing RON |
| `CHANGELOG.md` | modding-visible format addition |

### Credit

| Path | Why |
| --- | --- |
| `crates/nova_assets/src/scenario/` | the built-in scenarios that could use it; regenerate with `content -- gen` if any does |
| `crates/nova_scenario/src/filters.rs` | if the new event carries scopeable data |
| `crates/nova_scenario/src/world.rs` | `NovaEventWorld`, the action's write surface |
| noting that gameplay-internal notification uses observer-on-marker, and `nova_events` is only for the scenario-observable boundary | this is the misread `AGENTS.md` invites |
| `crates/nova_events_macros/` | the `EventKind` derive, if the new kind needs it |

### Why this task discriminates

This is the events-vs-observers test. `AGENTS.md`'s "Cross-subsystem
communication through `nova_events`, not direct coupling" reads as a general
mandate; it is not one, and the crate doc says so. An agent that proposes
routing internal gameplay signals through `nova_events`, or that puts the
`OnDocked` emitter in `nova_scenario`, has the direction backwards -
`nova_scenario` depends on `nova_gameplay`, not the reverse.

Second signal: the action lives in two places at once - a config struct plus a
`match` arm plus a prelude line. Missing the `match` arm in
`actions/mod.rs:92` is the classic incomplete answer - one required surface,
so Completeness lands near `0.67`.
