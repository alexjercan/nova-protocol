## Part 1: the save cost (branch only; NOT a matched A/B)

Master has no `WorldSaveSession`/`snapshot_world` equivalent at all
(`nova_world_base::save` does not exist on `master`) - this section is a
one-sided reading of the branch's own save cost, never a comparison.

Method: `examples/systems/system_world_resume.rs`, default (`create`) phase,
which runs the create walk (New Game, inject fixture, cross a sector, fail
and retry a leave save, fire the three live combat transients, leave) and
then spawns and waits for its own `--phase load` child in one process - the
same two-phase shape SW-PT9.md round 8 ran. Built once with `cargo build
--example system_world_resume --features debug,trace -j 8` (8m37s, confirmed
buildable - this was itself a live question going in). Each of the 5 repeats
is a fresh `cargo run` of that same binary (`CARGO_TARGET_DIR=./target`,
scoped to the branch worktree), serialized, with:

```
DISPLAY=:119
VK_DRIVER_FILES=VK_ICD_FILENAMES=.../lvp_icd.x86_64.json
ALSA_CONFIG_PATH=/tmp/nova-p7/empty-alsa.conf
NOVA_AUTOPILOT=1
NOVA_AUTOPILOT_DEADLINE=300
TRACE_CHROME=/tmp/nova-p7/part1/run<N>/trace.json
RUST_LOG=bevy_ecs=trace,nova=debug,info
```

`snapshot_world` (`nova_world_base::save::session::snapshot_world`,
`crates/nova_world_base/src/save/session.rs:315`) is an exclusive system that
runs every frame a `WorldSaveSession` resource exists (`run_if
resource_exists`) and returns immediately most frames - only a frame that
actually has a wanted save to serialize does real work
(`crates/nova_world_base/src/save/session.rs:251-253`). **The reported
`calls`/`mean_ms` below therefore mix hundreds of near-zero early-return
frames with the handful of real serializations; `max_ms` and the top-5 list
are the honest read of the actual save cost, not the mean.** This was
confirmed by code reading, not assumed.

Trace size per repeat was ~6.9-7.0 GB (the module's own "routinely gigabytes"
warning, `crates/nova_probe_cli/src/evaluation/profile.rs:29-35`, held). No
probe-CLI entry calls `aggregate_system_costs` on a standalone trace file
outside the `probe run` harness (`nova_probe_cli/src/evaluation/artifacts.rs:156`
is the only call site, and it is wired to a `probe run` child's own
`trace.json`, not to this example, which is uncataloged - not in any
`[[example]]` Cargo.toml block, so `probe run` cannot target it at all). Used
the sanctioned fallback: a short streaming script,
`/tmp/nova-p7/trace_system_cost.py`, reading the chrome trace line-by-line
(each line is one JSON object; the top-level array is never materialized),
replicating `aggregate_system_costs`'s B/E-stack-pairing and X-event logic for
one target system name.

File sizes: a small watcher
(`/tmp/nova-p7/watch_sandbox.sh`, polling every 0.3s) ran beside each repeat
to `stat` and copy every `state.N.ron` the run's own sandbox wrote, because
the harness deletes the sandbox on PASS
(`examples/systems/system_world_resume.rs:1331`,
`std::fs::remove_dir_all(&sandbox)`) - confirmed by code read and by run 1,
where the watcher (first version, `-maxdepth 3`) missed the sandbox's
`worlds/<slug>/state.N.ron` nesting by one level and the PASSed run's sandbox
was gone by the time I looked; fixed to `-maxdepth 4` for runs 2-5. Run 1's
sizes are therefore **not available** - flagged rather than filled in with a
neighboring run's numbers.
