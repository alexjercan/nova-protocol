The gates went red unobserved

Master does not build green, and has not for some part of this window. Both failures are mechanical. Neither needs a design decision. Both block every other finding here, because nothing downstream can be verified against a tree that will not compile under the lint.

Root cause

The working rule is to skip local Clippy and the full test suite, because the suite OOMs this box. That rule saved a lot of wall clock and it also removed the only local signal that either gate had moved. Nothing replaced it.

The Clippy failure is a documentation lint, not a code lint. A continuation line in the reload module's header turns the three lines below it into unindented list items:

crates/nova_assets/src/reload.rs:20–253 errors
//! What IS driven here is the cover. Sixteen files re-read and a registry
//! rebuilt cost more than a frame, and paid in the open they read as a freeze
//! - so [`ContentReload`] runs the reload as a small machine: the panel goes up
//! on the press, the read waits until it has been rendered, and the resource
//! lives until the files have landed and the frame after the merge came back
//! smooth. `nova_core` draws the panel for as long as the resource exists.
// clippy::doc_lazy_continuation -- the dash at line 22 opens a list item,
// so 23-25 must indent to continue it, or the dash must go.

Because nova_assets is a dependency, it fails first and the wasm job never reaches nova_editor. Suppressing just that lint to see past it exposes eight more:

Save and open are not inverses

The editor lowers a document into a scenario file and lifts it back. Those two operations disagree about what belongs in the file. Lowering composes the scenario from the document plus module constants and unconditional injections; lifting reads only the file. So the document you reopen is not the document you saved.

−A standing ship that was. The same function filters standing ships on !ship.sections.is_empty(). An empty ship the builder placed deliberately does not survive the reload.
+Handlers for objects that are gone. sandbox_events chains PICKETS and SKY_BEACONS from module constants regardless of document contents.
Root cause

sandbox_objects and sandbox_events serve two masters. They build the thing you fly, where injecting a player ship and the stock pickets is right, and they also build the thing you save, where it is wrong. One function, two contracts.

The third injection is the sharpest, because it produces a file the game refuses to load. Delete a seeded picket, save, and the file still carries handlers naming it:

The runtime content gate then does exactly its job. lint/scenario.rs:168 builds satisfiable from spawn ids only; check_filter and check_target raise LintSeverity::Error; merge.rs:313 files them into ContentIssues; and loader/lifecycle.rs:126 refuses the load with a FAILED TO START modal. The saved range is dead from the Scenarios menu.

DECIDED
A second Player ship silently drops the first. scenario.rs:381 lowers with ShipDriver::Player => fleet.player = lowered, so the last one wins and the earlier is gone with no warning. Decided: the builder refuses a second Player ship, so lowering never has to pick a winner. The silent-loss path stops existing rather than getting a warning.
HELD
A prototype section forks to inline on focus-out alone. inspect.rs:934 rewrites node.source to Inline before it attempts any write, and text_field.rs:246 submits when a field loses focus. Held: no prototypes exist yet and none are planned for v0.12.0, so the rewrite is inert. Revisit when prototypes land — this is the trap waiting for them.
MAJOR
A docstring states the opposite of the code. bundle.rs:134 says the pilot is carried "so flipping a ship to AI and back does not lose them". bundle.rs:219 substitutes AIControllerConfig::default() for both the Player and the None arms. True in memory, false across the file.
Decided
let's not allow multiple player ships in editor builder
Shift: a lowering fix becomes a builder constraint — smaller, and it removes the failure mode instead of handling it.
Blocker Read 1 finding decided

Play skips the gate the game runs

This is why the cluster above could ship. The editor's Play button and the Scenarios menu reach the same runtime by different roads, and only one of them passes the content lint.

crates/nova_editor/src/scenario.rs:206–232setup_scenario
let scenario = sandbox_scenario(&game_assets, world_objects(..), &lower_fleet(..));

if let Some(mut scenarios) = scenarios {
    scenarios.insert(scenario.id.clone(), scenario.clone());   // no lint
}
commands.trigger(LoadScenario(scenario));
// ContentIssues is written by the merge (merge.rs:313), which this path
// never enters -- so on_load_scenario finds no errors for this id and
// starts a scenario the same content, loaded from disk, would refuse.
Root cause

The lint lives in the merge, not in the scenario. Anything that reaches LoadScenario without passing through register_bundles is unchecked by construction. The editor is the only such caller, and it is precisely the tool whose output most needs checking.

Decided
content lint on load … it's the same way Wesnoth does it, it lints the scenario when you load it; but at the same time it also does a check at startup/F5, so we should do the lint in both cases

So the lint moves to where the load happens and stays where the merge happens. Two gates, one lint: on_load_scenario lints the config it was handed instead of consulting a table someone else filled in, and the merge keeps its bulk pass so a broken mod is reported at startup rather than at the moment you click it.

Shift: this is the cheapest fix on the page relative to what it buys. It converts the whole round-trip class from "a player finds it, later" to "the editor refuses it, now" — and it is the proof harness the round-trip work is verified against.
Blocker Read 1 finding decided · scope grew

Every key system guards itself

There is no arbiter deciding which keyboard consumer owns a keystroke. Each system carries its own hand-written guard list, and a mode nobody thought to add to a list is a mode that does not suppress anything.

keybind.rs:381 · placement.rs:276 · lib.rs:175the collision
// keybind.rs -- an armed rebind takes any key except Escape
keys.get_just_pressed().find(|k| **k != KeyCode::Escape)

// lib.rs -- delete_key is guarded by exactly two conditions
delete_key.run_if(not(typing_into_a_field).and(in_state(Editor)))

// An armed rebind is neither typing_into_a_field nor a state.
// Pressing Delete to BIND Delete also runs delete_key.
Root cause

typing_into_a_field is a guard for one specific modal consumer. The rebind is a second one, added without a corresponding predicate. A third will have the same problem: the guard list grows by hand, so the default for anything new is "suppresses nothing".

Decided
we should probably have some modifiers, like in vim you have visual, normal, insert mode … when I go into "bind" key it should no longer send WASD to the camera … basically going into BIND MODE if you will; and we need something like this probably in multiple places, like maybe even nova os?

An input mode owns the keyboard while it is active, and every consumer asks the mode rather than carrying its own denial list. Bind mode swallows everything but its own exit; camera, placement and shortcuts go quiet without knowing bind mode exists. The delete-during-rebind defect stops being reachable rather than being patched.

Shift: the largest scope change on the page — a one-line guard fix becomes a subsystem. It pays for itself the moment a second modal consumer exists, and text entry, the gallery and Nova OS are all already that.

Two pixel spaces, one comparison

ComputedNode::size() is physical pixels. Node::left and Node::top are logical pixels. On a 1× display they are the same number, which is why this reads fine on the machine it was written on and misplaces every world-anchored element on a HiDPI screen.

the same loop, four times3 wrong, 1 right
ui/rail.rs:375    let scale = computed.inverse_scale_factor();   // correct

ui/plate.rs:257   computed.size()   // raw physical, compared to logical
ui/callout.rs:156 computed.size()
keybind.rs:225    computed.size()
Root cause

The world-anchor loop — project a world point, measure the element, clamp it inside the viewport — is written out longhand in four places. One of them learned about the scale factor. The other three were copied before that, or from each other. This is the DRY finding and the HiDPI defect in one: extract the loop and there is exactly one place left to get the units right.

Also in this family: ui/window.rs:41 places the colour picker at size.x - RIGHT_MARGIN - WINDOW_W with RIGHT_MARGIN = 264.0 against an inspector PANEL_W = 300.0. The picker overlaps the inspector by 36 px at every window width — the error is width independent, so no monitor escapes it.

Decided
we need a pass on the UI to make sure it renders properly regardless of resolution, so it's more responsive; now obviously it's all landscape resolution, not really vertical, so at least we have that as a small goal
Shift: from three unit fixes to a bounded responsiveness pass. Landscape only is the useful half of that bound — it keeps the pass from becoming a full portrait layout rework, and makes "correct at any landscape resolution and DPI scale" a goal that can actually be finished.
Major Read 5 findings decided · scope shrank

The reload counts what it cannot name

ContentReload tracks outstanding re-reads as a usize and decrements it by the number of Modified events seen. It never checks which files those events belong to, so a straggler from an abandoned reload closes the next one early.

crates/nova_assets/src/reload.rs:207–219settle_reload
let landed = events.read()
    .filter(|event| matches!(event, AssetEvent::Modified { .. }))
    .count();   // a count, not a set of ids

if reload.phase == ReloadPhase::Reading {
    reload.pending = reload.pending.saturating_sub(landed);
    if reload.pending == 0 { reload.phase = ReloadPhase::Settling; }
}

// reload A caps out at 6s with one file still in flight; the resource is
// removed. The builder presses F5 again. A's straggler lands and closes
// one of B's slots -- so B uncovers while a file of its own is still out,
// and the merge frame runs in the open.
Root cause

The whole machine exists to hide a long merge frame from a player who is mid-game. Every subtlety in it — the count, the dwell, the settled-frame heuristic, the hard cap — is there to reload without a real loading screen.

Decided
what I expect is F5 to work only in the main menu, and when I hit F5 the game "blocks" so it goes into the loading screen; it should be similar to restarting the game basically; same to when I exit the mods menu, or also when I exit the sandbox editor or a scenario from playing

That removes the premise. A reload that is allowed only from the main menu, and that blocks into the real loading screen, is the boot path with a different trigger. There is no frame to hide, so there is nothing to time.

Shift: the fix is to delete the machine, not to make it count correctly. Three of this cluster's five findings stop existing:
DISSOLVED
F5 works mid-flight (plugin.rs:195 has no GameStates gate and no clock pause). Gone by design: F5 is main-menu only.
DISSOLVED
A save during a cover is silently dropped (reload.rs:124 swallows any request while one is in flight, including the three that have just written new bytes). Gone by design: the triggers become screen transitions — leaving mods, the editor, or a scenario — which cannot overlap a blocking load.
DISSOLVED
The stray-file miscount and the untested counting half. Gone by design: a blocking load waits on the asset server the way boot does, with no per-file bookkeeping of its own.
SURVIVES
Silence when a file never comes back. Whatever replaces the cap still needs to say which file did not return, or a mod with a RON syntax error is an unexplained wait. The log that reports bundles plus content as a content count (:170, :182) goes with it.
Held Read 3 findings unmeasured

Rebuilt every frame, changed rarely

Three editor systems recompute derived state on a cadence set by the frame rather than by the thing they derive from. State this plainly: no frame was measured in this review. These are shape arguments, and the cost of each is unknown.

Decided
not sure here, I would rather have something more like immediate mode for certain things, but fair, what can be cached safely we can cache; though the editor doesn't lag right now, it feels fine as FPS goes, so IDK, depends here

Correct instinct, and it splits the cluster cleanly. Two of these are speculative optimisation against an editor that does not lag — no measurement, no complaint, no work. The third is not a performance finding at all.

KEEP
gizmo.rs:322 — GizmoReach::measure invalidates only when the selected entity changes, so an inspector resize leaves the handle hit-test where the gizmo used to be. This is a correctness bug wearing a performance costume: a cache keyed on the wrong thing. Immediate mode fixes it, and so does a correct key. Either answer is fine; leaving it is not.
HELD
node.rs:460 sections_of collects and sorts per ship per frame, calling id_order on both sides of every comparison. node.rs:1209 report_duplicate_ids takes an unfiltered Query<&Children>, so it walks every parented entity in the world. Held until a probe run says they cost something. Optimising an editor nobody has seen stutter is how simple code stops being simple.

Three of the review's own corrections landed here and set the ceiling on severity: sync_inspector and sync_scene_list are not unconditional — lib.rs:513 gates the tuple on in_state(Editor).and_then(not(gallery_open)); sync_editor_probe self-guards at probe.rs:203; and the unconditional reload on leaving the Mods panel is deliberate per its own comment. None of it touches a player flying a scenario.

Major Read 2 findings decided · scope grew

The inspector writes the unholdable

Reflection-driven editing gives every field an editor for free. It also gives every field an editor whether or not the value behind it can survive what the box accepts.

crates/nova_editor/src/inspect.rs:305–323number_rule
// x, y and z return None -- no floor, no ceiling, no finiteness check.
// Every Position, Rotation and Scale box accepts NaN and inf, and a
// pasted inf propagates straight into the transform.

The second is not a validation gap but a duplicated control. inspect.rs:1002 lists "aim" among the picks for a Light, while node.rs:325 states outright that a light is aimed by its node rotation and ships with aim: None. Two controls drive one output, the gizmo is the one the builder can see, and nothing indicates which won.

Root cause

The pick list and the leaf rules are two independent hand-kept tables describing the same types. A field can appear in one without the other noticing, which is how a vector leaf got an editor with no rule and a light got a second aim control. And every leaf renders as the same control — a text box — so the type's constraints have nowhere to live.

Decided
we should try to be precise about what gets edited and what not; also would like if we can get more advanced inputs, rather than just textboxes … dropdowns, number inputs with drag to increase/decrease, sliders, some kind of validators on the fields that can be interpreted by the editor's inputs so that we can do better validation, like min value, max value, format etc … something cool is the color picker, get some inspiration from that

One table, not two: a field declares what it is and what it accepts, and the editor picks the control from that declaration. A bounded float gets a slider or a drag-number that cannot leave its range; an enum gets a dropdown instead of a spelling test; a colour already has the picker, which is the proof the pattern works. NaN stops being a validation bug and becomes a control that cannot express it.

Shift: from two defect fixes to a field-rule system. The precision half — deciding what is editable at all, and dropping aim from the light — is the same table, so it comes along rather than being separate work.

Open3 questions, with a default for each

Still open

None of these blocks starting. Each has a default I will take if you say nothing.

How does the builder refuse a second Player ship?
Default: refuse the driver change and say why, matching how an occupied socket and a blocked drive lane already refuse. The alternative — silently demoting the previous player to AI — is the same silent mutation the finding objects to, one level up.
Do sub-tasks 6 and 7 belong in this task?
They are features, not review fixes: an input-mode subsystem and a field-rule system are each larger than the eight findings that prompted them. Default: keep them in the parent as sub-tasks, since that is what you asked for, and schedule them last so the review fix can land green without waiting on them.
How far does the comment sweep reach?
Default: this range only — the 88 commits since v0.11.0, which is what "we started to add them again" describes. A whole-tree sweep is a bigger diff than every behaviour fix on this page combined, and it would bury them.

What this review did not do

  • Nothing was measured. No probe run, no --samply, no baseline compare. Every performance claim here is derived from code shape — which is why the frame cluster is held rather than scheduled.
  • Nothing was flown. The red-team and feel lanes were not dispatched. That is the --play pass, scheduled after the fixes.
  • Two of thirty findings were proven by execution — the two red gates. The other twenty-eight are read from the tree, including all three of the remaining blockers.
  • Lanes were build-free by design. Thirteen agents on one target/ and one GPU would serialise on the cargo lock and corrupt any frame number, so all building and testing was serialised into the main session. That is what surfaced the Clippy failure, which no lane reported.
  • Not reviewed at all: tasks/**, .agents/**, .claude/**, and the Reflect derives on the nova_scenario config types against what the editor's reflection walk needs.
