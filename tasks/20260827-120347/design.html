Task 20260827-120347 · design

Reaching into the game by name

A second language on the same CRT: one curated command catalog that inspects the run, writes the player's settings, and runs a bounded set of cheats that mark the run out loud. The process channel types the same lines and reads the same answers back.

v0.13.0priority 50console / input / toolingwritten 2026-09-02

What this is not It is not arbitrary EventActionConfig execution. The scenario enum is an authoring vocabulary and stays one; a new action does not become a command by existing. The catalog below is the whole public surface, and every row on it was put there on purpose.

01One emulator, two shells

The CRT was already a terminal: casing, glass, phosphor, sound, forwarded pointer, scrollback, prompt, caret, completion ghost, staged welcome rows, every editing key, and the pause it takes while it is open. All of that is the EMULATOR and none of it is NOVA OS. The temptation was a second console-looking overlay; that would have meant a second line editor, and two line editors drift.

So the terminal grew a ShellKind and a per-shell ShellSession, and the split falls exactly where the two languages differ.

The emulator ownsA shell owns
casing, glass, phosphor, the open/close animation, the cue soundsits command registry
the line editor: typing, Backspace, Home/End, history keys, Tab, PgUp/PgDnits prompt prefix (nova> / cmd>)
the pause, the freed cursor, and Escape while openits transcript and its history
the header and the right-hand status stripits header text and its staged introduction

Switching shells therefore keeps the picture up, keeps the freeze, and restores the other shell's scrollback and history exactly. It does not replay the power-on animation, because nothing powered on.

Settled — open decision 1

Escape climbs one level, and the level you came in on is where the ground is.

Entering Commands from a NOVA OS prompt makes NOVA OS the floor: Escape returns to nova>, and a second Escape powers off. Opening with : makes Commands the floor: one Escape closes the computer, because climbing into a NOVA OS session the player never opened would be inventing a room.

02Where the code lives

The third open decision, and the one with the longest shadow: a dispatcher that reads ships, writes settings and arms cheats touches nearly every crate. Put it in nova_os and the terminal model — today a leaf that a headless test can build in a line — drags gameplay, scenario and menu behind it.

Settled — open decision 3

Split the language from the executor. nova_os keeps the words; a new nova_console runs them.

nova_os holds the catalog metadata, the parser, the structured CommandResult and the CommandChannel bus, and stays a leaf. nova_console holds everything that touches the world, and sits ABOVE nova_menu because a graphics or volume command writes the very resources the settings screen owns — one of the two has to be downstream, and it is not the menu.

The payoff shows up on the wire: nova_channel depends on nova_os for the LANGUAGE and never on nova_console. A tool that only wanted to type a line does not pull in gameplay.

One ordering constraint holds the whole thing together: ConsoleSystems::Dispatch runs .after(NovaOsSystems::Input).before(NovaOsSystems::Simulate), so a line typed this frame is answered and painted this frame. The channel submits in PreUpdate, so a wire command is dispatched in the same frame and acknowledged after that update().

03The class is the permission model

Four classes, checked once, at the top of the dispatcher. There is no per-command permission code to forget to write, and there is no cfg(debug) anywhere near it: the shell and the wire have the same vocabulary in a shipped build as in a developer one. A cheat that only exists in debug is a cheat nobody had to be honest about.

Every row carries its own metadata — name, usage, summary, class, arity, worked examples — and parsing, help, completion, the commands listing, the introduction's registry count and the wiki page all read that one table. The examples are load-bearing: a test walks every documented example of every command back through the parser, which is how help ammo refill section was caught failing on its own arity.

04Arming marks the run, one way

cheats enable is the deliberate act, and it marks the run at the moment it succeeds — not at the moment a cheat is used.

Marking on benefit was the alternative and it is worse in both directions. A player who armed and then thought better of it still played a run that could have been anything; and a mark that only lands on use gives the refusal nothing true to say, so it has to pretend the command does not exist. Marking on the ask lets the refusal be honest: this is a cheat, arm it if you mean it, and know what arming costs.

The mark is one-way for the same reason. There is no command that unmarks a run, because a run that was armed was never clean. What DOES clear it is a new run: scenario load <id> abandons the current attempt without assigning it an outcome and without advancing campaign progress, then resets the arming and the mark together.

05What turning unlimited ammo off gives back

Unlimited fire works by REMOVING the magazine, because “no SectionAmmo” is already the game's word for a weapon that never runs dry. That leaves one question, and the task named it as an open decision.

Settled — open decision 2

Restore the section's AUTHORED capacity, full, with the reload re-seeded and no cycle in flight.

The alternative was putting back the round count from the moment the cheat was armed. It was rejected because that count is not a state the world was ever in: while the cheat is on the weapon never spends a round, so restoring a stale number invents a half-empty magazine out of a fight the player did not have. Full is what the magazine effectively held the whole time.

SuspendedSectionAmmo carries the authored capacity and the reload config across the suspension, and only sections that HAD a magazine carry it — so a weapon authored unlimited stays unlimited when the cheat goes off.

The cheat is a scenario action underneath (SetInfiniteAmmo), which is the point: it replaces the old infinite_ammo flag on the player controller, which was authored once at spawn and honored only under the debug feature. An action instead of a flag works on a LIVE ship, works in a shipped build, and lets authored content ask for the same thing in the same words. RefillAmmo is its bounded half: it restores what a magazine holds instead of removing the magazine, so a resupply beat does not have to grant unlimited fire.

06The wire says the same words

The channel does not get a vocabulary of its own. It carries the exact text a player would type, resolved by the same parser, run by the same dispatcher, and answered with the same structured result.

in · command

{"tick":120,"command":"graphics low"}
{"tick":121,"command":"cheats enable"}
{"tick":122,"command":"ammo infinite player_spaceship on"}

The same line, character for character, that the CRT accepts.

in · action

{"tick":120,"action":{"SetAllegiance":...}}
→ error: `action` is not a wire lane and
   will not become one; use `command` and
   the command catalog

Permanently refused. v0.12.0 refused it with “the console vocabulary is task 20260827-120347”; that task is this one, and the answer is that the key never opens. 

// out · the acknowledgement names the command, not its internals
{"line":22,"command":"ammo infinite","class":"cheat","state":"ok",
 "detail":"player_spaceship: 2 weapons unlimited",
 "rows":["player_spaceship: 2 weapons now fire unlimited."]}

A caller never learns which scenario action ran underneath, which is what keeps the internal action free to change. rows is what the screen printed; detail is the one-line summary; the class is there so a driver can assert it never armed anything by accident.

07What is deliberately absent

Seven capabilities that exist as scenario actions and are NOT commands. The list is short and the reasoning is one sentence each, so that adding any of them later is a decision somebody makes on purpose.

08The creative map, and what it turned up

The run mark and the scenario classification are different subjects and stay apart. A shell cheat accuses the PLAYER; an authored scenario action never does — but content that injects world state is worth reporting, so the linter computes it.

One exhaustive match over all 28 actions is the single source of truth: own_injection() returns a name for an action that injects and None for one that only does bookkeeping or presentation. effect() and collect_injections() both derive from it, so they cannot disagree, and Sequence has no class of its own — it carries whatever its steps carry. Ten actions inject: SpawnScenarioObject, ScatterObjects, DespawnScenarioObject, CreateScenarioArea, SetSpeedCap, SetControllerVerb, SetAllegiance, ForceTorpedoLaunch, SetInfiniteAmmo, RefillAmmo.

A creative map is CONTEXT on the report, never a finding, and never touches the lint's exit code.

Open — for the owner With that classification, all 18 scenarios in the tree are creative maps, because SpawnScenarioObject and ScatterObjects are what every scenario does to exist at all. The per-action classification is correct on its own terms and meets the stated bar — no bookkeeping or presentation action is classed as injection — so it ships as written, and the report prints each scenario's ACTION LIST rather than a bare verdict. But the ELIGIBILITY rule built on top of it needs revisiting before any badge is shown to a player: a signal that fires on everything carries nothing. The likely fix is to score the actions that reach into a RUNNING world — the six ship-state ones, which only four scenarios use use — apart from the spawning that merely furnishes one.mdash; apart from the spawning that merely furnishes one.
