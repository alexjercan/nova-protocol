1. Summary and top recommendation

source Today the player docks by hand: the mouse turns the hull through the camera rig, Shift enters RCS fine-adjust (translation in the hull frame, heading frozen in the world frame), and D asks for capture against the travel lock. Nothing holds motion or attitude relative to the target. STOP kills world velocity, not relative velocity. The NPC DockApproach already flies the target's frame, but it closes and holds the pair for the AI. A player cannot reach it.

Top recommendation proposed: one player-armed assist that makes the target body the pilot's frame of reference: the hull moves with the target's point under the hull's centre of mass. It has two parts.
  1. Velocity part: while armed, the RCS trims the relative velocity back to the value the pilot last left it at.
  2. Attitude part: only while RCS fine-adjust is held, the frozen heading co-rotates with the target. The heading includes the roll the pilot chose with Q/E.
The assist never closes the gap, picks a port, aligns an axis, changes the pilot's roll relative to the target, or presses D. On a target that spins about the hull's nose, co-rotation turns the hull in the world frame with it. That is following the target, not roll alignment. It runs on the finite RCS magazine and shows one status word.

Why this shape: it removes the target's own motion (drift, orbit, tidal pull, spin) from the problem. It leaves the skill of a stationary-target dock unchanged: square the plates, close the gap, press D. The existing MatchVelocity and Autopilot paths do not fit. In normal flight, a manual burn start or a Shift press removes the Autopilot. The exceptions are pause, suspended control, a docked hull without the helm, and Shift on a hull without RCS (flight_rig.rs:422-441, 725-750), so an autopilot-based assist could not run beside manual control.

6. Physics, budget and units

RCS budget modeled

  • Full deflection is 5 x 9.81 = 49.05 m/s2, so 300 m/s lasts 300 / 49.05 = 6.1 s of held full input (state.rs:764-766 says "about six seconds").
  • A full refill needs 2 s idle + 300 / 100 = 3 s, so 5 s with no command. An assist that trims every tick never lets the magazine idle.

Tidal hold cost modeled

Relative to a free-falling station, a hull at distance d feels a tidal difference of about omega2d (across the orbit) to 2 omega2d (along the radius). The source cites a 73 s orbit (autopilot.rs:2168-2170), so omega = 2 pi / 73 = 0.0861 rad/s and omega2 = 0.00741 s-2.

So the hold is affordable close in and expensive far out. The seed 29 station's orbit period was not recovered, so the model and the measurement are not a matched pair. The linear model over-predicts far out: at 3,250 m it gives 24 to 48 m/s2, against 11 measured. The source comment gives 3 to 8 m/s2 within a few hundred u. Do not use the model beyond about 1 km. This is the reason for a range gate and a visible empty state, not for a drive fallback: a drive hold turns the hull, which breaks the attitude part and takes the heading from the pilot.

Co-rotation vs the capture speed gate modeled

The capture gate compares the two roots' LinearVelocity (port.rs:237). source That is centre-of-mass velocity: Nova says so at autopilot.rs:228-233, and avian 0.7.0 velocity_at_point adds omega x r to it (registry avian3d-0.7.0/src/dynamics/rigid_body/world_query.rs:31-38). The recommended hold uses the target's point velocity at the hull's COM, so it follows a spinning target. A hull rigidly co-rotating with a target spinning at omega, with centres d apart, has relative spin 0 but relative speed omega x d. The 5 m/s gate then caps omega at 5 / d: 2.86 deg/s at d = 100 m, 1.43 deg/s at 200 m. Above that, a perfect co-rotating hold cannot capture. The pilot would need to stop co-rotating at the last moment. This is a property of the current gate, not of the assist. If the hold used the target's COM velocity instead, the hull would not follow the port's swing and this limit would not apply. Owner decisions 3 and 7 cover it.

Units and named edges

  • Author the range and any rates in meters (Meters, MetersPerSecond). Convert once in FlightSettings::default with to_engine(), as rcs_accel does (state.rs:825-828). One engine unit is 10 m.
  • Flight math stays in u and u/s (avian Position, LinearVelocity). The HUD converts with MetersPerSecond::from_engine (flight_status.rs:11-15). The bench converts in docking_view (observation.rs:545-585).

8. Recommended first slice and API sketch

proposed Slice 1 = velocity part + status + bench telemetry. Slice 2 = attitude part + camera rig. Splitting them gives a clean manual vs velocity-only bench comparison before any helm change.

// UNAPPROVED SKETCH - names, fields and placement are owner decisions.
// crates/nova_ship/src/flight/state.rs
/// The player's relative-frame assist; absent = off.
#[derive(Component, Clone, Copy, Debug, Reflect)]
pub struct FrameMatch {
    /// The body whose frame is held: the travel lock at arm time.
    pub target: Entity,
    /// Held velocity relative to the target's point under this hull's COM
    /// (body_point_velocity), in the target's local frame, u/s. Re-latched
    /// on every tick the pilot commands RCS.
    pub velocity: Vec3,
    /// q_target^-1 * q_ship, latched when RCS fine-adjust starts (slice 2).
    pub attitude: Option<Quat>,
}

/// What the assist did this tick: read by the HUD chip and the bench.
#[derive(Component, Clone, Copy, Debug, PartialEq, Eq, Reflect)]
pub enum FrameMatchStateType { Holding, Dry, Range, Lost, NoRcs, NoHelm }

// FlightSettings: frame_match_range (authored Meters, value = decision).

// Shared pure helper, extracted from DockTarget::frame_velocity
// (autopilot.rs:228-236) so the NPC and the assist read one law:
pub(crate) fn body_point_velocity(v: Vec3, spin: Vec3, com: Vec3, point: Vec3) -> Vec3;

// Systems, inside NovaFlightSystems (flight/mod.rs:210-235):
//   manual_burn_system -> drive_frame_match -> rcs_burn_system
//   drive_frame_match writes a per-tick RCS trim (new field or component:
//   decision) so decay_player_rcs_intent never decays assist output.
//   hold_frame_attitude (slice 2) writes ControllerSectionRotationInput
//   and rotates the Normal rig by the same delta while RcsActive.
// Observers: arm/disarm verb (flight_rig.rs), remove FrameMatch on
//   Add<Autopilot>, Add<DockedShip>, burn Start, TravelLock change.

Why the trim stays separate: RcsIntent is the pilot's decaying input (manual.rs:28-33). Mixing the trim into it would leak assist output into the next tick's pilot input. This means rcs_burn_system's input changes first (the owning interface), and its callers follow the compiler errors.
