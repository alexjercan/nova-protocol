The shapeOne transport, three vocabularies

The whole design turns on one asymmetry: an input goes through the game's rules and can legitimately fail; an action bypasses them. Only the first is built here. The other two lanes are drawn because the schema has to leave room for them — a vocabulary added after drivers exist is a parse break, while one reserved and unused costs a match arm.

input — through the rules

{"tick":1200,"input":"radar_hold","phase":"start"}
apply(name, phase) → press the bound source

Resolves through the registry to a live Binding and presses it. Conditions and modifiers still run, so a driven radar hold is a real Hold. It can do nothing — radar destroyed, magazine empty — and that is the point.

action — around the rules task 120347

{"tick":1200,"action":{"VariableSet":{"key":"act", …}}}
serde → EventActionConfig → run it

Would parse the same enum the RON parses, so all 26 actions arrive with zero per-action work and the two can never drift. Deferred: it is a console feature that stdin happens to reach, not a stdin feature.

command — beside the rules task 120347

{"tick":1200,"command":{"SetGraphics":"low"}}
the process, not the world

Graphics presets, replay speed, window size. It touches nothing the simulation can see, so it neither marks a run nor makes a scenario ineligible. Named here because the schema has to leave room for it; nothing is built for it in this task.

Merging the namespaces would lose the guarantee that makes an input test prove “a player could do this”. Keep them apart even though one transport will carry all three.

The same three exist in the GUI, on different surfaces: keys carry input, and a console carries the other two. Without a window there is no keyboard and no console, so one transport carries all three. That is why stdin looked like it was inventing a vocabulary — it is not; it is the only place all three are visible at once.

The namespace is already a field, so nothing gets renamed

A flight_* prefix is the right read and it costs nothing, because ActionBinding already carries group separately from name — it is what the settings list headings are built from. Address on the wire as <group>.<name>, lowercased: flight.autopilot_goto, targeting.radar_hold, camera.free_look.

Renaming the fifteen instead would be a save-file break for no gain. Persisted rebinds are keyed by these strings, and apply_overrides SKIPS a name the build no longer has (a_saved_binding_for_an_action_this_build_lost_is_skipped), so a rename silently discards whatever a player had moved. Deriving the prefix keeps the grouping and the save file.

Section bindings have no global name — they have a section id

There is no main_thruster action and there never was one. main_drive is the flight computer's burn intent (FlightIntent.burn); it is not a thruster trigger. What fires a section is a per-section component, SpaceshipThrusterInputBinding(Vec<Binding>), snapshotted onto the section entity from the content input_mapping and driving one ThrusterInput action per section (nova_ship/src/input/player/weapons.rs).

So the addressable identity is the AUTHORED SECTION ID, and two sections on one ship can carry different keys with no name in common. The shipped corvette binds turret_port and turret_starboard both to LMB; nothing stops a mod binding Q and E. The snapshot already prints ships[].sections[].id, so the id half is free — only the binding half is new.

Which is why firing has no row in the registry table above, and cannot have one. It still needs to be written down, so here is what the shipped corvette actually carries — the same two rows every combat scenario builds from CARGOA_TURRET_IDS:

Read the table as an example of the FORM, not as a fixed control scheme — the ids and the keys are content, and a mod replaces both.

Axes are not presses, and the code already says so

rcs_aim declares mouse motion plus the LEFT stick; camera_rotate declares motion plus the right stick. Neither declares a discrete source, so the settings rows read “Mouse / Left Stick” and “Mouse / Right Stick” with no chip a capture could take, and dispatch::apply refuses both with NoButton.

They therefore need their own lane carrying a delta rather than a phase. And that lane has a scheduling constraint a press does not: bevy REPLACES AccumulatedMouseMotion / AccumulatedMouseScroll every frame, so an axis write is worth exactly one frame and must land after(InputSystems).before(EnhancedInputSystems::Prepare). A press survives across frames and needs only the first half. 

{"tick":1200,"aim":{"name":"flight.rcs_aim","delta":[3.0,-1.0]}}

Typing and pointing are transport, not vocabulary

A driver still has to type map at the NOVA OS prompt and click Resume in the pause menu. Neither belongs in the registry. A registry action is a REBINDABLE PLAYER VERB — a name, a label, a Controls row, a line in the settings file. There is no verb behind the letter h, and giving the alphabet rows would bury the thirty-three real actions under a hundred nobody can move.

An “any key” action does not rescue it either, and the reason is sharper than taste: a typed character has NO KeyCode. type_text writes key_code: KeyCode::Unidentified and carries the letter in logical_key, because that is the only way to tell h from H — the same physical key. InputSource::Keyboard(KeyCode) cannot represent it, so such a row would have nothing to bind, nothing to persist and nothing to print. bevy_enhanced_input does offer Binding::AnyKey, and BindingSpec already excludes it for the same reason: it means nothing in a save file.

The technical half decides it anyway. dispatch::apply writes ButtonInput and nothing else. The prompt reads KeyboardInput.logical_key — that is how it tells h from H — and bevy_picking builds a click out of WindowEvent::MouseButtonInput. Neither ever looks at ButtonInput, so the action lane physically cannot type or click, whatever it is named.

Over stdin that beats raw pixels badly — a driver writes click "Resume" instead of guessing coordinates that shift with the layout. The named form should be primary and raw pixels the fallback, for the same reason press_action beat press_key.

The wrapping is not free — no window, no typing

type_text resolves a PrimaryWindow to stamp on the event and warns out if there is none. --norender sets primary_window: None, so under exactly the mode the channel exists for, every one of those helpers is a no-op.

The reader does not care, though: handle_terminal_keyboard filters on the prompt being active, the state being Pressed and the logical_key, and never reads event.window at all. So the channel writes the same event with a placeholder entity and the prompt takes it. The fix is to make the window optional on the helper rather than to require a window the headless path deliberately does not have. Pointer input is the harder half of the same problem, because bevy_picking DOES resolve a window and a camera.

Several lines may share a tick, and they apply as a set

Simultaneous presses need no schema change: the transport is one JSON object per line, lines are grouped by tick, and a tick's inputs are applied together before the tick runs. A set, not a sequence — ButtonInput is itself a set, so there is no ordering within a frame to express even if the schema offered one.

Anything genuinely order-dependent already needs separate ticks, and the game has a worked example: raising_inside_the_tap_window_latches_the_combat_slot. The radar latches the stance at the HOLD THRESHOLD, not at the press, so “Ctrl, then raise 100 ms later” and “both at once” are different gestures with different outcomes. That distinction lives in the tick numbers, which is where it belongs.

The read half: the snapshot advertises what can be pressed

A driver should not carry a copy of this table — that is the same mistake the fifteen hardcoded example files were making, in a different process. Two additions make the channel self-describing:

  • input.actions[] in the header — name, group, label, current keyboard and gamepad sources, axis kind. Sorted by name, like every other snapshot list, so it stays byte-identical for diffing.
  • ships[].sections[].binding — the section's live binding list, next to the id the snapshot already prints.

Then a driver reads what it may press and what each is currently bound to, instead of assuming a control scheme. It also makes a rebind observable: the same script against a remapped profile can be told what moved.

The open questionsDecisions

Q1 — the line schema

One JSON object per line, both directions. In: a tick and exactly one of input, action or command. Out: the snapshot, plus an applied block.

capture_snapshot already emits a schema-versioned header (schema, scenario, frame, elapsed, game_state, reason). The channel adds one field and invents nothing else. 

// in
{"tick":1200,"input":"radar_hold","phase":"start"}
{"tick":1260,"input":"radar_hold","phase":"stop"}
{"tick":1260,"action":{"StoryMessage":{…}}}   // parsed, refused, 120347

// out (one per snapshot; body elided)
{"schema":1,"frame":1260,"elapsed":21.0,"reason":"step",
 "applied":[{"input":"radar_hold","phase":"stop","state":"Fired"}],
 "ships":[…],"ordnance":[…]}

How an input reports failure. The dispatcher cannot know whether the game acted; it only presses a key. So applied carries each named action's live TriggerState after the frame evaluates — None, Ongoing, Fired. A driver reading "state":"None" knows the press did nothing, and the rest of the snapshot says why. An unknown name is a script error in any lane and logs loudly.

Why all three keys are parsed today. A reserved lane answers “not in this build yet, see 20260827-120347”. An unreserved one answers with a parse failure indistinguishable from a typo. The first is a version negotiation; the second is a bug report. Externally tagging the lane by key — rather than a "kind" field beside a payload — is what makes the later addition purely additive: a new key is a new variant, and every existing line still parses byte for byte.

Q2 — which crate owns the stdin reader

Two new crates, neither of them debug-gated: nova_input below nova_ship for the registry, nova_channel above nova_scenario for the reader and the snapshot. nova_probe depends on them, never the reverse.

Not nova_probe. It is an optional dependency behind the debug feature and the manifest says so in as many words: release/dist builds never carry it. Headless mode is not debug-gated in the same way — AppBuilder::new() reads NOVA_NORENDER unconditionally, so any build boots headless from the environment, and only the --norender CLI flag needs the feature. Putting the reader in nova_probe would mean the one mode with no keyboard also has no way to be driven in the build players get.

Not nova_ship either. A ship crate has no business owning a table of action names. It happens to be reachable from the settings menu, which is a dependency-graph accident, not a reason.

And not one crate for both. The registry and the reader cannot share a crate, because the graph puts them on opposite sides of nova_ship: the registry must sit below it, since nova_ship, nova_scenario and nova_menu all build from it; the reader must sit above nova_scenario, because the action vocabulary is EventActionConfig. One crate holding both would be a cycle.

Q3 — step mode, and who waits

The simulation thread never blocks on a read. A reader thread owns the blocking read_line; the game only ever does try_recv. Step mode then gates the CLOCK, not the read.

Reading stdin is a poll, always. A line arriving on the channel should feel exactly like a keypress: the loop ticks at its own rate, drains whatever is waiting, applies it, and carries on. That is what a multiplayer server does with an idle client, and it is the behaviour that ships. std::io::Stdin has no portable non-blocking read, so the blocking call is parked on a dedicated thread and reaches the simulation through an mpsc channel — the process has a thread in read(), the game never does.

Step mode is a separate, opt-in clock policy. It exists for one reason the poll cannot solve: an LLM thinks for seconds and the game runs 60 ticks a second, so a free-running world has moved hundreds of ticks before the reply lands and the observation describes a game that no longer exists. Step mode holds the clock — it does not halt the loop, which keeps polling, keeps its shutdown line live, and can time out and say so. 

loop {
    while let Ok(line) = rx.try_recv() { queue.push(line); }   // never blocks
    if stepping && !queue.has_tick(next_tick) { continue; }    // gate the CLOCK
    for _ in 0..n { app.update(); }        // ManualDuration, fixed dt
    sink.write(capture_snapshot(app.world_mut(), "step"));
}

Still a custom runner rather than an exclusive system in First: the runner already owns exit handling, and a gate that lives inside a frame cannot decide whether the frame happens. TimeUpdateStrategy::ManualDuration keeps dt off the wall clock either way. Warm up with one update first — the first manual update reports dt 0.

That gives the tick field two readings, and the mode picks which. Free-running, a tick is an ASSERTION: a line stamped 1200 that arrives at 1263 is applied late and the lateness is reported, so a driver learns it cannot keep up. Stepping, a tick is a SCHEDULE: the clock waits for it, which is what makes the same script replay to the same result.

Q4 — which cheats are catalog actions · moved to 20260827-120347

All of them, and the question splits in two. Did the player reach in? marks the RUN. Does this script inject world state? makes the SCENARIO a creative map. Different subjects, different answers, and only the first one accuses anybody.

Answered, then handed on. None of it is buildable without the console, so it belongs with the console. The working is kept below rather than discarded — it is the reason the follow-up task starts from a position instead of a blank page.

The bar this question started from — would a scenario genuinely want it? — answers a different question than the one asked. It is a good test for what belongs in the base game. It is the wrong test for what a modder may reach for, because a modder who wants god in their mod has a legitimate reason: it is their mod.

So the catalog documents everything, cheat-class actions in their own section carrying what they cost. An undocumented action is strictly worse than a documented cheat: it still exists, it is still reachable, and now nobody can find out what it does without reading the source.

One addition. kill_all should not be a verb at all: it should be the existing entity filter with a destructive effect, so “kill all raiders” and “kill everything in this area” come free and it reads like every other action. A blunt verb would be the only action in the catalog that cannot be scoped.

Deferred · task 20260827-120347The action vocabulary

Everything from here to the crate layout describes work this task no longer does. It is recorded because it was reasoned through with the tree open, and because a decision reached and then forgotten gets made worse the second time. The follow-up task carries the same list.

Why the locked door stops working

The codebase already has one cheat, and it takes the opposite approach. infinite_ammo is honored only under the debug feature; a shipped build logs a warning and keeps the authored magazines (objects/spaceship.rs). The cheat is compiled out of the game people play.

That works while authoring a scenario is the only way to reach a cheat. The channel ends it. The channel ships in release — that was the whole finding behind the crate split — so a released build now has a way to invoke any action by name. Gating actions on cfg(debug) would make the vocabulary differ between builds: a driver written against a debug build would fail on a release one with a missing verb rather than a refusal. That is precisely the failure the single-vocabulary decision exists to prevent.

The consequence Once the door cannot be locked, marking is not the softer option. It is the only one that keeps every build's vocabulary identical to every other build's.

Two subjects, and keeping them apart

It is tempting to run these on one switch. They are not the same thing, and collapsing them produces an accusation where none is warranted:

A mod built around god is that mod working exactly as authored. Its author is not cheating and neither are you for playing it. It is simply a scenario where a completion time means nothing — so it carries a badge, its runs never reach the stats, and it stays fully playable and fully shareable. That is the whole penalty, and it is the right size.

Arming, the Minecraft way

The precedent worth copying is that enabling cheats is one deliberate act on the world, not a judgement made per command. You turn it on once, the world is flagged from then on, and afterwards the commands simply work.

Same here. The action lane is refused until the channel is armed, and arming is what sets the one-way bit, at the moment you ask for it. That gets the ordering right: the run is marked by a decision made knowingly and up front, not discovered forty minutes in. It also gives the refusal something honest to say — “this needs the channel armed, and arming marks the run” beats a missing verb.

Where eligibility does need a class — and a correction

The tempting shortcut is “every scenario action is a cheat, so eligibility needs no field”. It does not survive contact with the enum. Every scenario alive uses Objective, VariableSet and Outcome — that is what a scenario is. Under that rule 100% of content is a creative map and the badge means nothing.

Sorting the 26 variants by the only question that matters — does it change the simulated world in a way playing could not have produced? — the split is lopsided, which is why it works:

nClassVariants
18bookkeepingObjective and its markers, VariableSet, the timers, Sequence, StoryMessage, HudReadout, HintEmphasis, DebugMessage, Outcome, NextScenario, SetCamera, Screenshot, SetSkybox. Scenario state and presentation. Nothing the ship can feel.

Eight variants to classify, not twenty-six, and the eligibility rule reads plainly: a scenario is a creative map if its script contains any injection action. Computed by the linter, never authored — nobody can write a cheat scenario that declares itself eligible.

The edge worth naming Outcome and NextScenario are bookkeeping in a script and blatant from a console — instant win, level skip. They need no class, because the origin rule already caught them: typed at the console they arrive on the action lane, and that lane always marks. Two rules, no overlap, no third case.

infinite_ammo stops being a ship field

It should be an action that grants unlimited ammunition, not a flag baked into the player ship's shape. A ship has no business carrying “someone cheated” in its own type; the missing magazine is the effect the action leaves behind, not a property of the hull.

Checked before proposing it: no shipped scenario sets it true. All six base .content.ron files and the example mod pass false. The only true sites are examples, which build with the debug feature — exactly the population the cfg gate was protecting. So the field can be dropped from SpaceshipController::Player at no cost to released content.

The real cost, stated Today the flag decides whether SectionAmmo is attached at spawn. As an action it must add and remove that component on live entities, which is a different code path and not a rename. That is the price, and it buys a cheat that is reachable, documented, and classifiable like every other one instead of a special case in the spawn path.

Two crates is not tidiness. It is the only arrangement the graph admits.

capture_snapshot moves with the reader for the same reason the reader moves: a release-mode driver that can press keys but cannot read the world is half a channel. What stays in nova_probe is the part that is genuinely diagnostic — the NOVA_PROBE_SNAPSHOT file sink and its frame schedule. The serializer already imports nothing from nova_core, so the move is a file move, not a redesign.

Armed by environment, not by feature

The channel ships in release and does nothing until a variable names it, the same contract every probe capability already keeps: an ordinary run wires nothing. That is what makes it safe to ship a stdin reader in a player build, and it is also what keeps the multiplayer option open — an input path that exists only under a cargo feature would have to be rebuilt the day anything else wants to drive the simulation.

Phase 1The bindings registry

Naming the rig's actions does not delete reference.rs by itself. The settings panel renders in the main menu, and no rig exists there — the flight rig spawns with the player ship. The structure that fixes that is a persistent registry the rig is built from, and it is the same structure rebinding and the dispatcher need. 

// nova_input: the one source of truth. The rigs read it; the settings
// menu reads it; the dispatcher resolves through it.
#[derive(Resource)]
pub struct InputBindings(Vec<ActionBinding>);

pub struct ActionBinding {
    pub name: &'static str,        // "radar_hold" - the channel's key
    pub group: &'static str,       // "FLIGHT" - the settings row header
    pub label: &'static str,       // "Radar Hold" - what a player reads
    pub keyboard: Vec<BindingSpec>,
    pub gamepad: Vec<BindingSpec>,
}
Not a cosmetic rename That field is called section today, on KeybindEntry in input/reference.rs, and the settings screen reads it as a row header. In nova_ship section already means a hull section — SectionAmmo, insert_turret_section, and the editor's apply_section_rebind, which really does rebind a ship section. One word, two meanings, in one crate. The registry replaces KeybindEntry outright, so this is the one moment the rename is free; later it is a churn commit nobody schedules.

Two blockers found in persistence

PersistedSettings is Copy. Adding a bindings map breaks that derive, and every use site that relies on it has to be audited in the same change. The serde-defaulted field itself is non-breaking; the Copy bound is the work.

Do not persist upstream Binding. It derives serde only behind bevy_enhanced_input's serialize feature, which this workspace does not enable — and three of its variants (AnyKey, Custom, None) are meaningless in a save file. Persist a nova-owned BindingSpec and convert at rig build, so the save format is not hostage to a dependency's variant list.

Phase 2The dispatcher, and what it may honestly claim

apply(name, phase) is a lookup and an injector, not an interpreter. It runs where the autopilot already injects — PreUpdate after InputSystems, so a synthesized press is still just_pressed when game systems read it.

There are two ways to make an action fire, and they are not interchangeable:

RouteMechanismConditions and modifiersVerdict
Source press the bound key / button run a driven radar_hold is a real Hold The default. It is what makes an input test truthful.
Mock ActionMock component skipped upstream is explicit: input reading, conditions and modifiers are all bypassed Not the default. It cannot prove a gesture, only a state.

That settles the audit's open question about whether the mock API composes with Hold and Tap: it does not compose — it replaces. So the dispatcher takes the source route, and the three source kinds with no press/release helper get one written rather than being handed to the mock:

  • Mouse motion (rcs_aim, camera_rotate) → write AccumulatedMouseMotion.
  • Wheel (component_next / component_prev) → write AccumulatedMouseScroll.
  • Gamepad → unverified; see the open list.

All three are read by bevy_enhanced_input as plain resources, the same way it reads ButtonInput, so writing them stays on the truthful path.

Correction to the round-4 audit

The audit's proof-of-done is “38 hardcoded call sites across 7 example files”. The tree today has 165 injection sites across 14 files — but only 12 of them press a flight or targeting key, in 4 files. The other ~153 are UI-walk gestures (LMB on a widget, Escape, Enter, Tab, typing) that are not named game actions and must stay raw. Porting them would be busywork that makes the harness worse. The real phase-1 target is those 12, plus raise_stance, plus the three separate copies of hold_radar — in hollow.rs, screenshot_radar_lock.rs and system_hud_indicators.rs, each hardcoding ControlLeft independently.

Phase 3The clock, and the snapshot sink

Two clock policies, one loop. Free-running is the default and the one that ships: the world ticks at its own rate and stdin is drained each pass, so a line lands like a keypress. Stepping is the opt-in policy for a slow driver — an LLM thinks for seconds and the game runs 60 ticks a second, so free-running the world has moved hundreds of ticks before the reply arrives and the observation describes a game that no longer exists. Stepping replaces the keyboard and the clock, and it does that by withholding app.update(), never by blocking a read.

The output half is mostly built. capture_snapshot(&mut World, reason) is confirmed pure — no IO, no mutation beyond the query state bevy builds to read it — and its module doc already anticipates this exact mode. Phase 3 is a runner and a sink, not a serializer; the serializer only changes crates.

The SyncWorldPlugin leak decides the session length

On the headless branch SyncWorldPlugin supplies a resource whose queue is never drained, because draining happens in the render sub-app's extract. That leaks ~24 bytes per synced spawn and per synced component removal — about 2.4 MB per 100k, linear in run length. PendingSyncEntity is pub(crate) upstream, so it cannot be drained from outside.

The call: bound the session and say the number. Ship a step cap, document the memory cost per 100k steps, and do not advertise indefinite driven sessions. Vendoring bevy or adding ExtractPlugin both cost more than the problem — ExtractPlugin would rebuild the mirror render world that --norender exists to avoid. Revisit if an upstream fix lands.

TrapsWhat this must not become

  • More unchecked runtime strings. Action names are exactly the failure this project has no compiler for: a rename compiles clean and fails at load. The registry must be covered by a test that asserts it names every action the rigs spawn, in both directions — a name with no action, and an action with no name, are both failures.
  • A network protocol. This is shaped like a multiplayer server's input path. That is a reason to keep the simulation clean, not a reason to add framing, versioning or auth. Nothing on the board points at multiplayer.
  • Scope inflation from the agent case. Rebinding and no-rebuild testing each justify the work alone. The agent is the third payoff, not the specification.
  • A simulation that waits on a human. Reading stdin must feel like a keypress: the world does not freeze because nobody has typed yet. Anything that parks the game thread in a read is wrong even when it happens to work for one driver — it forecloses the multiplayer option, and it cannot time out or answer a shutdown line. Stepping earns its wait by gating the clock, in one named mode, with the loop still live.
  • NOVA OS as the console. It cannot be: opening it freezes the game deliberately, so it can never drive a live one. Share the dispatcher, not the surface, and do the console last.

SequenceOrder of work

  1. nova_input, and build the rigs from it. The new leaf crate, the registry, and the four callers switched over. No behaviour change, no new surface. Lands with the coverage test and the reserved-sources computation. Unblocks the settings task on its own.
  2. Settings reads the registry. Ten mirror rows die; five are declared fixed. Persistence lands here, with the Copy audit and BindingSpec.
  3. Dispatcher. apply(name, phase), the three new source kinds, and the port of 12 call sites plus three hold_radar copies.
  4. nova_channel: the runner and the stdout sink. Free-running first, stepping as a flag on top of it. capture_snapshot moves here and nova_probe starts depending on it. Bounded sessions, documented cost.
  5. stdin transport, input only. Three lanes parsed, two of them reserved and refused with a clear error, plus the applied block and replay-by-tick. The lanes land together; adding one after drivers exist is a parse break.

Five steps, not six. The console and everything that hangs off it is 20260827-120347.

Done when the settings menu reads keybinds by action name rather than from a mirror; a range drives the game through the dispatcher instead of a raw KeyCode; and a headless run emits world state, accepts named inputs on a channel, and replays the same input sequence to the same result.

Note what the cut did not cost. Pressing named inputs and reading world state back is the whole of “a driver can play this game”. The action vocabulary was the convenience layer on top, and it is the half that needed the console anyway.
