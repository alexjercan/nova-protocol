The bindings registry

One table that says which named player actions exist, what each is called on screen, which physical sources it occupies, and when it can fire at all. Every rig is built from it, every rebind surface reads it, and driving an action by name is a lookup in it plus a press.

The two rulesWhat the crate is

A leaf, and it has to stay one

bevy and bevy_enhanced_input, nothing else. The rigs are built from the table and every rebind surface reads it, so it must sit below all of them. nova_scenario already depends on nova_ship; a crate that also held the process channel would have to sit above nova_scenario too, and that is a cycle. The channel is a separate crate for exactly this reason.

A resource, not a property of the rig

The settings panel renders in the main menu, where no rig exists — a bevy_enhanced_input rig spawns with the player ship. The same fact is why the NOVA OS toggle and the HUD cycle are polled through InputSources rather than driven by a rig: the monitor has to open with nothing on the field.

Defaults stay pure data. Each owning crate exposes its list as a plain function, and the plugin turns those into the live table, so the content lint — which has no world — calls the function instead.

The shape of a rowThree axes, not one

An action carries a name, a group and a context, and they are close enough to be mistaken for each other. They are not the same axis, and collapsing any two of them breaks something specific.

fieldAnswersRead byWhy it is its own field
nameWhich action is this? The wire, the save file, every lookup Persisted rebinds are keyed by it. A rename is a save-file break: apply_overrides SKIPS a name the build lost, so it silently discards what a player moved.
groupWhere does it print? The settings headings, the wire prefix FLIGHT, TARGETING and CAMERA are three headings a player reads apart. Address as <group>.<name> and the prefix is free.
contextWhen can it fire? The live set, the conflict check Those same three headings are ONE firing context: they go live together and go quiet together. Deriving it from the group would make a display change a behaviour change.

Why the context had to exist

Every action resolves to a key, and keys are reused across surfaces on purpose. Three actions hold G. Two hold W. Two more hold each of [ and ].

So handing a driver the whole table tells it one key means three things at once, and pressing an action that is not live does not fail — it presses the key, and whatever IS live reads it as its own action. Asking for flight.autopilot_goto with the map open sets a GOTO on the map instead. The list has to be the live one.

The check this bought

Both fixed rigs run with consume_input: false, so two actions on one source drive both at once. The old guard compared gamepad buttons inside the flight lists alone, which is how rcs_modifier and combat_stance sat on Left Trigger 2 unnoticed. conflicts() pairs only actions whose contexts overlap, so it can read the keyboard half too and run over all 33 without flagging the keys flight shares with a surface it can never be up beside. It reports rather than refuses: radar_hold and radar_clear share Ctrl on purpose, one gesture read two ways.

The viewer actions carry no pad binding, and that is deliberate rather than unfinished. They never had one: the monitor is a keyboard surface, and inventing pad buttons here would reserve them against the flight rig for a gesture nobody asked for. The edgesWhat is deliberately not in here

Escape

The universal back-out at every rung, and the one key that stays hardcoded. A rebind could strand a player inside a mode with no way out. It is the only row left in the settings screen’s fixed list.

Typing and pointing

There are three input transports in this tree that do not see each other: ButtonInput, which is what the dispatcher writes; KeyboardInput.logical_key, which is what the NOVA OS prompt reads to tell h from H; and WindowEvent::MouseButtonInput, which is what bevy_picking builds a click from.

So an action physically cannot type a character or press a button on screen — it writes to a resource neither of those readers looks at. Typing and pointing are transport, not vocabulary, and they get their own raw lanes on the channel.

Firing a section

There is no fire_primary and there never was. What fires a section is a per-section component snapshotted from the content input_mapping, so the addressable identity is the authored section id and two sections on one ship can carry different keys with no name in common. The corvette binds turret_port and turret_starboard both to LMB and Right Trigger 2; nothing stops a mod binding Q and E.

The seamThis crate defines; the channel shows

nova_input answers two questions and stops: what actions exist, and which of them can fire right now. It hands back live() and conflicts() and does not act on either.

Advertising the live set and refusing a name outside it is nova_channel’s job, because that is where a caller with no window exists at all. The dispatcher stays an injector rather than an interpreter for the same reason: it presses what it is told to press, and every example driving an action by name goes through it with no protocol around it.
