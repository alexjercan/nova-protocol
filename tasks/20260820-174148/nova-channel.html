Playing Nova by wire

Everything a player does with a keyboard, a mouse and a screen, done over stdin against a --norender process: named actions, axes, typing at the NOVA OS prompt, and clicking buttons that were never drawn. What the tree already provides, what each gap costs, and runnable proof-of-concept drivers against a mock of the wire.

v0.12.0steps 4–5 of the sequencePoCs in tasks/20260820-174148/poc/written 2026-08-27

The process channel settled the shape: one JSON object per line, the input vocabulary only, a reader thread that never blocks the simulation, a step clock for slow drivers. The bindings registry shipped the vocabulary and the dispatcher. This round answers the owner’s widening question for the crate that does not exist yet: can a driver on stdin do everything the GUI player can — move the mouse, click Resume, type map at the prompt — and what does the headless assembly have to grow for that to be true rather than aspirational?

Everything below was read off the current tree (bevy 0.19.0, bevy_picking 0.19.0) while writing. Claims that were traced through source but not yet executed were tagged spike; later rounds RAN all six spikes against the real app (the section at the end holds the transcripts), and rows they proved now read ran. The crate round then built nova_channel for real: the pointer and NOVA OS drivers pass against the shipping binary over --channel step — the end of this page holds what shipped and what is still open.

The findingOne virtual window buys the whole pointer

The parent page left pointer input as “the harder half” with a note that the fix is to make the window optional on the helpers. The investigation says the opposite: make the window exist. Headless input dies in three independent places, and all three are the same missing entity.

BlockerWhereEffect headless
Every gesture writer resolves PrimaryWindow nova_autopilot/src/input.rs:102-108, 401-409, 527-534 type_text, press_edit_key, set_cursor, set_mouse_button, turn_wheel all warn and no-op
No camera ever computes target_info bevy_render camera.rs:351-435; bevy_ui update.rs:137-153 UI layout gets a 0×0 viewport; every node’s ComputedNode::size() is zero
ui_picking matches pointers to cameras by render target bevy_ui picking_backend.rs:126-131, 184-186 a window-targeted camera never normalizes, and zero-size nodes are skipped anyway — no hits, ever

Call — the virtual primary window

When the channel is armed, spawn one ordinary Window + PrimaryWindow entity with a fixed resolution. No winit, no surface, no render — just the component.

This works because none of the three consumers wants a real window; they want the ECS record of one. get_render_target_info reads window.physical_size() and the resolution’s scale factor off the component (bevy_render camera.rs:275-284) — no GPU, no winit. With that one entity: camera_system normalizes WindowRef::Primary and fills target_info; layout gets a real viewport and every percentage-sized menu resolves to real pixels; ui_picking matches the camera; and every nova_autopilot gesture helper — click_named, move_cursor, type_text, the cursor pin — comes alive unchanged.

It is also the established idiom, not an invention: nova_os_ui/src/pointer_rig.rs:240-246 spawns exactly this entity to drive the real forward_nova_os_pointer through the real ui_picking in a windowless test app, and nova_autopilot/tests/pointer_pin.rs:105-130 does the same for the picking chain. Spike 1 (system_headless_pointer) now boots the FULL app that way, and it passes: the pause overlay lays out at 1280 × 720, Resume resolves to a real 238 × 40 box, and the click resumes the game through the observer.

Rejected: the RenderTarget::None { size } route (retarget every UI camera, write PointerInput by hand) is real — upstream documents custom pointers as a supported path, bevy_picking input.rs:1-12 — but it touches every camera spawn in five crates to avoid one entity, and it forks the code path between windowed and headless runs. The virtual window keeps them identical, which is the property every “a driven test proves a player could do this” argument rests on.

Two more facts make the pointer cheap. mouse_pick_events builds picking from WindowEvent messages alone — it never touches winit (bevy_picking input.rs:121-201) — and the whole picking stack is already in the headless build: --norender is full DefaultPlugins minus only WinitPlugin (nova_core/src/lib.rs:202-230), so UiPlugin, UiPickingPlugin, UiWidgetsPlugins and PointerInputPlugin are all present and idle, waiting for events that today never come.

The stanceWhat gets bypassed, and what must not be

The owner’s framing question for this round: does the channel have to simulate the GUI, or can it use the in-memory backends the game already keeps and bypass the presentation — send “what happens when you press the button”, the way a multiplayer packet would? The answer the tree gives is: the backends already exist, and the wire already speaks at both of the levels that question names.

Nothing here simulates graphics. --norender is backendless — wgpu.backends = None, no render sub-app at all (nova_core/src/lib.rs:520-533) — and what survives IS the model layer: NovaOsTerminal is a plain resource with prompt() and active_mode(), the pause menu is a tree of taffy rects, the CRT texture nobody draws is only a projection of state that lives in components. The virtual window is not a fake screen; it is a 16-byte size record that makes “on screen” a well-defined question for the layout that already runs.

The named-input lane is the packet level: {"input":"flight.main_drive","phase":"start"} goes straight into the dispatcher, no keyboard anywhere, and the context check is the validation — a verb whose context is not live is refused, not pressed blind. That is “apply what the button does”, with the server-side rule the multiplayer analogy asks for.

The pointer and text lanes are the human level, and there bypass is refused on purpose. Triggering a button’s Activate observer directly would happily press a button that is hidden, off-screen, or inside a menu that is not open — a driven test would pass on exactly the broken UI it exists to catch. So pointer to "Resume" works the way Playwright’s click(selector) does: resolve the Name to a laid-out, visible, non-zero rect (the shipped ui_node_rect already refuses hidden and degenerate targets and warns on ambiguous names), then synthesize the REAL events at its centre and let picking decide what is under them. Reachability is part of the contract, not an obstacle to route around.

Rule of thumb the ledger follows: anything the game itself models as a named action goes over the packet lane; anything that is genuinely a device gesture — typing at a prompt, clicking a rect, dragging a slider — goes over the device lanes through the full pipeline, so the run proves a player could have done it.

The gateHeadless has no NOVA OS to type into

Call — the UI plugins go render-aware, not render-gated

Give NovaOsUiPlugin and NovaHudPlugin the { render: bool } shape every other game plugin already has, and add them on both branches. Superseded by spike 2: the run showed neither plugin needs a flag at all — every GPU-side piece is already bevy-guarded — so this branch simply removes the gate. Whether headless measurement runs want the flag anyway (probe noise) stays an owner call; see the spikes section.

The convention exists precisely for this: NovaGameplayPlugin, NovaShipPlugin and NovaScenarioPlugin all take render and gate their own device-touching pieces internally. The NOVA OS crate is closer to ready than its gate suggests — its render-dependent systems already carry resource_exists guards (terminal/mod.rs:278, 311, 320), the terminal MODEL (nova_os) has no render dependency at all, and the slide animation runs on Time<Real> on purpose. What the spike must prove is the rest: spawning the CRT surfaces and RTT cameras with no GPU behind Assets<Image>.

The alternative — register the bindings unconditionally but keep the systems gated — is worse than the bug. The table would advertise verbs that do nothing, which is the one kind of lie the registry was built to end.

Related but distinct: with a virtual window present, the two Single<&mut CursorOptions, With<PrimaryWindow>> pause systems (nova_menu/src/pause.rs:108, 130) stop being silently skipped and start operating on the virtual window’s cursor options — harmless, but it belongs in the spike checklist, not in a surprise.

The wireFive lanes in, acknowledged out

The parent page fixed the envelope — one JSON object per line, exactly one payload key beside tick, action and command parsed-and-refused. This round fills in the raw lanes it named. A tick is required on every line in step mode (it is the schedule); free-running it is optional and late application is reported.

input — a named verb, or a section

{"tick":120,"input":"targeting.radar_hold","phase":"start"}
{"tick":180,"input":"targeting.radar_hold","phase":"stop"}
{"tick":200,"input":"section.turret_port","phase":"start"}
dispatch::apply · press and hold across frames

Addressed <group>.<name>, resolved against the registry; section.<id> resolves the section’s own SpaceshipThrusterInputBinding off the ship instead. One start, one stop — a hold is two lines, not a line per frame.

aim — a delta, not a press

{"tick":121,"aim":{"name":"flight.rcs_aim","delta":[3.0,-1.0]}}
apply_axis · worth exactly one frame

Bevy replaces the accumulators every frame, so a sweep is a line per tick. The registry decides which way the wheel turns; the driver only says how far.

text — characters into whatever has focus

{"tick":300,"text":"map"}
KeyboardInput per char · text + logical_key + a Released twin

The prompt reads event.text; TextField reads Key::Character — each event carries both, so one lane types into either. Never touches ButtonInput: a character has no KeyCode.

key — one literal editing key, as a tap

{"tick":301,"key":"Enter"}
{"tick":320,"key":"Escape"}
both halves · message and ButtonInput, press then release

Enter, Tab, Backspace, Delete, the arrows, the page keys, Space, Escape. Written to both readers because the tree splits them: the prompt and the fields read the message, the mode chords and the rebind capture poll ButtonInput. A held key is not this lane — holding is what named actions are for.

pointer — move, press, release, wheel

{"tick":400,"pointer":{"to":"Resume"}}
{"tick":401,"pointer":{"press":"left"}}
{"tick":402,"pointer":{"release":"left"}}
{"tick":410,"pointer":{"to":[640,360]}}
{"tick":411,"pointer":{"wheel":-2.0}}
the autopilot pointer helpers against the virtual window

to takes a Name — resolved through the same census the snapshot prints — or raw logical pixels as the fallback. A click is three lines on three ticks, because Activate fires on release-over and the forwarded pointer documents a frame of lag; the PoC client wraps the idiom.

tick — bare, the step instruction

{"tick":500}
stepping: run the clock to here, then snapshot and wait

Input lines schedule their own ticks implicitly; a bare tick is “nothing more from me until then”. Free-running it is a no-op. EOF in step mode is an exit — the clock could never advance again; free-running, EOF just closes the lane and the game plays on.

What comes back

{"schema":1,"reason":"step","frame":181,"scenario":"...","game_state":"Playing","elapsed":3.0,"t_real":3.02,
 "applied":[{"line":7,"input":"targeting.radar_hold","phase":"stop","state":"Fired"}],
 "input":{"live":["camera.camera_rotate","flight.main_drive","targeting.radar_hold","..."],"contexts":["always","flight"]},
 "ui":{"pause":"Unpaused","computer":null,"targets":[{"name":"Resume","rect":[576,312,128,36]}]},
 "ships":[...],"ordnance":[...]}

{"schema":1,"error":"`action` is reserved; the console vocabulary is task 20260827-120347","line":9}
  • applied — every line consumed since the last snapshot, echoed with its outcome. For named actions that is the action’s TriggerState after the frame evaluated (None / Ongoing / Fired), which is how a driver observes “the press did nothing” without the channel pretending to know why.
  • input.live — InputBindings::live(&ActiveContexts), the actions that can fire THIS tick. Pressing outside it is refused by the channel rather than pressed blind, because a dead name still presses a live key — three actions hold G.
  • ui — the screen a GUI player sees, as data: the pause rung, the terminal model when NOVA OS is up (mode, prompt, cursor, parse status, completion hint — all already public on NovaOsTerminal, state.rs:265-292), and the pointer census: every Named node that is visible and non-zero, with its resolved rect — the same filter ui_node_rect already applies. This is what makes pointer to "Resume" honest: the driver clicks what it was told exists.
  • Errors — an unknown name, a malformed line or a reserved lane answers on stdout with the offending line number, and logs. A refused input (not live) is not an error line; it is an applied entry with "state":"refused", because being told no is part of playing.
  • All of this is additive on the existing snapshot — the schema policy says new fields need no version bump (snapshot.rs:127-130).

The plumbingTwo writers, two slots, one clock

The lanes do not share a schedule position, because their readers do not. Getting this wrong is invisible in a demo and fatal in a replay, so it is pinned here as the crate’s system layout.

SystemSlotWhy there
channel_pointer_writer First · after(MessageUpdateSystems) .before(PickingSystems::Input) mouse_pick_events consumes WindowEvent in First; writing later costs a frame of lag per gesture. This is the exact slot repin_cursor already occupies (input.rs:455-463).
channel_input_writer PreUpdate · after(InputSystems) .before(EnhancedInputSystems::Prepare) Bevy clears the just_* edges in InputSystems, so a press staged earlier is wiped before Update reads it — the autopilot’s slot, with the axis half of the constraint stated too, because the accumulators are REPLACED in the same set. Keyboard messages for the text/key lanes are written here as well: their readers are Update systems reading the message stream, same frame.
the runner around app.update() Drains the reader thread’s mpsc, gates the clock in step mode, calls capture_snapshot after the frame, writes the line. Installed with app.set_runner() after AppBuilder::build() — last runner wins, no plugin surgery (ScheduleRunnerPlugin only calls set_runner itself, schedule_runner.rs:73).

The freeze model cooperates instead of fighting: pausing stops Time<Virtual> and Time<Physics> but schedules keep running (nova_menu/src/lib.rs:198-200 says so in as many words — it is what keeps the pause overlay interactive). So the channel types into a frozen NOVA OS and clicks a pause menu with no special case: frames advance, the world does not, and the snapshot shows elapsed holding still while frame climbs.

Typing has three sharp edges, all found in the tree

  • Every synthesized keyboard event needs a Released twin. keyboard_input_system mirrors the message stream into ButtonInput<KeyCode> / ButtonInput<Key> and nothing ever releases what type_text presses — today every driven example leaves a trail of permanently-pressed phantom keys. Latent there; a correctness bug in a channel that also polls ButtonInput. The channel emits the twin.
  • Ctrl swallows characters at the prompt (terminal/input.rs:314) — so the input lane holding a Ctrl-bound action (radar_hold) while the text lane types is a driver error the doc has to name: the characters go nowhere, exactly as they would for a player holding Ctrl.
  • Home and End do not exist at the prompt — the arms are Enter, Tab, Backspace, Delete, arrows, page keys (terminal/input.rs:211-340). TextField handles them (text_field.rs:346-347). The key lane passes both through and promises nothing the reader does not.

The clockStep mode, and the seed that is not there

The runner shape is settled on the parent page — reader thread owns the blocking read_line, the game only ever try_recvs, stepping gates the clock with TimeUpdateStrategy::ManualDuration and a warm-up update. The investigation adds two facts to it.

Manual time is greenfield in the shipping app. All ~24 ManualDuration uses in the tree are inside test modules; no example and no binary path steps time manually today. The runner is the first, which is why the PoCs mock it rather than pretending a flag exists.

Correction to the parent page — determinism is not free yet

The replay argument leans on “composes with the seeded-bevy_rand rule”. The shipping app is NOT seeded: EntropyPlugin::<WyRand>::default() (nova_gameplay/src/plugin.rs:74) seeds from OS entropy, and every with_seed in the tree is a test rig. Same-input same-result needs a seed knob on NovaGameplayPlugin wired to a channel parameter — small, but load-bearing, and it did not exist on anyone’s list until now. Closed by spike 3: the knob is NOVA_SEED (owned by nova_gameplay::settings, on the env contract, a non-u64 value refuses the boot), and the replay range proved two seeded runs digest the world byte for byte.

Housekeeping with teeth, found the same way: any NOVA_* variable the channel adds (arming, step mode, the seed) must be registered in tests/env_contract.rs and docs/environment-variables.md or CI fails the build; and the SyncWorldPlugin queue still leaks ~24 bytes per synced spawn and removal headless (nova_core/src/lib.rs:212-229), so sessions stay bounded with the cost documented — unchanged call, now the channel’s to carry.

The proofFour drivers against a mock of the wire

Every schema line above is pasted from their transcripts, not invented. When the crate exists, the drivers point at nova --norender instead via --cmd and the mock retires into a schema reference.

The crate round: shipped

crates/nova_channel exists (commit f5708bd1): the protocol parser with the mock’s refusal texts as unit tests, the five lanes applied by two writer systems in the pinned slots, the stdin reader thread, and the step/free runners behind a boot gate — asset loading is wall-clock IO, so the runner holds the wire until GameStates::Loading ends plus two settle frames, and tick 0 is the world, ready. The binary arms it with --channel step|free (debug-only, requires --norender), installed after the builder so its runner wins. Each action entity now carries an ActionName tag out of InputBindings::bundle, which is what lets the ack read the named action’s TriggerState after the frame. The ui census moved out of the drivers into capture_snapshot as designed (pause rung + gated terminal model + named rects with the button flag + the CRT glass slice), and the header grew t_game — virtual seconds, the one clock that freezes with the pause states; elapsed is the scenario event clock and runs on its own cadence (it stalls through the shakedown’s opening beats, a scenario truth, not a channel one).

Acceptance so far: drive_pointer.py and drive_novaos.py PASS against the real binary and the mock alike, same script, only --cmd added. The real world corrected the mock in five places, each now folded back: the pause button is Resume Button; the NOVA OS group lowercases with an underscore (nova_os.* wire names); the terminal close is a 0.22 s CRT drawer, not a flag flip, so the driver steps through the slide; the press-to-pause transition spends two real frames before t_game freezes; and a press/release pair yields two acks, so “did it fire” reads the start ack, not the latest. A 120-tick flight.main_drive hold moved the real ship from rest to 15 m/s on −Z with the ack walking Fired → None.

The acceptance round: all four drivers pass

The flight pair got its world (commit 46530b9a): acceptance.content.ron, a loose --scenario-file beside the drivers — one armed corvette, one hostile raider_1 parked 280 u down the burn line under a long engage grace, each turret on its own free key so section.<id> presses one mount and never its neighbour. drive_flight.py and agent_loop.py now play the real binary against it, checks said in 3-D, and refuse to run without --cmd. Getting them green surfaced two real gesture rules the mock never knew: the radar sweep commits into the COMBAT slot only while weapons are raised (stance-down it banks a travel lock), and the lock is not the 0.25 s threshold alone — an acquisition dwell (0.6 s base, range-scaled) must charge on the candidate under the boresight, so the aim beat moved after combat and the hold grew to 90 ticks. The agent hunted the raider down in eleven half-second rounds: burn while far, stance up, sweep, both turrets on the lock; the raider ended defeated and neutralized with the player untouched. Free mode’s late flag is real too: a passed-tick line lands in ChannelFrame::late_lines and its ack says late, unit-tested at the ack funnel. The poc README now retires mock_game.py into the wire’s executable schema reference — the pointer and NOVA OS drivers still run against it without --cmd.

The recording round: the run becomes a movie

The branch landed (983d076c), and the hand-test question — what does a driven run look like? — got a better answer than a window: --record <dir> (commit 0a215e3f). A third assembly, AppBuilder::offscreen(), keeps the headless shape — no winit, no OS window, the channel’s virtual PrimaryWindow — but arms the GPU and the full visual stack, with pipelined rendering disabled so a stepped update() returns with its frame drawn. The recorder retargets every primary-window camera into one window-sized image, and the runner spawns one Screenshot of it per tick, each with its own numbered save_to_disk observer — capture completion order cannot scramble frame order. After EOF the runner pumps until the in-flight captures land, and channel.py stitches <dir>.mp4 with ffmpeg on close. One tick is 1/60 s, so the movie plays in real time however slowly the driver thought between steps.

Retargeting surfaced two integration truths, both fixed in the recorder rather than the game. First: with no IsDefaultUiCamera in the world, bevy_ui routes roots to the highest-order camera targeting the primary window — after retargeting, no camera at all, so the HUD vanished from the frames and every UI hit-test died. The recorder now marks the camera that fallback would have picked and stands down whenever the game marks its own (the menu ambience rig, the render-scale blit). Second: PointerInput::receive re-applies the frame’s window-targeted messages onto PointerLocation in PreUpdate, so the pointer’s retarget sits between ProcessInput and Backend — any earlier and it is clobbered on exactly the frames a gesture arrives.

The egui half ran as its own lane (commit abec9467): the debug inspector’s egui stack now assembles only when WinitPlugin is present, which takes the per-frame “Cannot access an underlying winit window” WARN from 230 occurrences per headless boot to zero — and covers the offscreen assembly with the same predicate for free.

Evidence: drive_pointer and drive_flight PASS recorded end to end; 415 gapless PNGs for the 414-tick flight; the frames carry the full HUD — the burn, the hostile target inspector, the tracer stream, the NEUTRALIZED overlay. The “playability runner” idea (one command: driver script + scenario in, video out) is deliberately NOT built and NOT nova_probe — probe asserts expected results, this produces evidence of play. It waits for next sprint’s agent-play task; until then the close-time ffmpeg is the pipeline.
