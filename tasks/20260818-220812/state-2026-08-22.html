02The one big win: a pristine fleet stopped paying for cracks

A cross-release comparison found broadside's p95 8.8% worse than v0.10.0, reproducing across five passes. The cause was structural, and the module doc asserted the opposite.

Damage cracks render through an ExtendedMaterial<StandardMaterial, Ext>, which is a separate render pipeline and cannot batch with plain StandardMaterial draws. Every section was swapped onto a cracks material the moment it existed - including bucket 0, the undamaged bucket. So an identically-sized scene drew through two pipelines where v0.10.0 drew through one, and it paid that whether or not a single shot had landed.

The module doc claimed the opposite. It said an undamaged fleet "batches as if the effect were not there". It did not. A doc that asserts a performance property is a claim like any other, and nothing was checking it.

The fix: at bucket 0 the mesh keeps its own source material and no cracked material is created at all. SectionCracks.material widened to Option<_> so None and bucket == 0 always agree, with a heal-back path when a damaged section returns to pristine.

Census gate passed before any timing: 65 extended materials to 0, meshes back on MeshMaterial3d<StandardMaterial>, EffectAsset 2 to 1. 24 of 24 metric pairs the same sign. Against the ablation that removed cracks entirely, the fix matches or beats it on every combat metric and is decisively better at p99 (-12.2% against -4.9%) - it keeps the feature and gives back the whole cost.

03The instrument was refusing the runs worth having

Every window of that A/B was refused by refresh_capped. The refusal was a false positive, and it had a direction.

The check refuses a window whose frame deltas collapse onto one value while the run had promised not to block on refresh - reasoning that what you measured is the display's period, reported as a completely plausible millisecond figure. Sound in principle. But it fires on steadiness, and an optimisation makes frames steadier.

It preferentially refused the faster arm. Probe certified 4/6 stock and 0/6 fixed on combat, 3/6 and 0/6 on idle. A comparison built from surviving windows would have had zero windows of the improved arm and reported no change - for a fix worth -8.6% mean.

Worse, it was structural rather than statistical: the refusal ran inside the capture and abort_capture returns five lines above emit_stats. A refused window wrote no JSON, no CSV row, no PerfRun. The arm did not get marked suspect - it vanished.

So the verdict moved to the repeat set, which is the only half holding enough captures to tell a period from a workload. The capture now records its cluster shape beside its stats and logs a suspicion; the set rules. checks.json carries the call under repeats.sets[].refresh_cap with the per-capture shapes beneath it.

04...and the premise that replaced it was also wrong

The discriminator was sold on "a refresh period is a CONSTANT, a workload is not". The first live run disproved the second half.

A 12-bay point-defence stress set produced suspect periods of 25.663 / 20.824 / 20.972 / 20.975 / 21.006 ms. Drop the first - the cold run, which the statistics gate discarded anyway - and the remaining four agree to 0.72%, inside the 1% that reads as one display. The set would have been convicted and emptied. It was acquitted by an outlier, not by the rule.

Share separates; agreement does not. So the bar moved 0.60 to 0.72 - above every workload measured, below every cap measured - and both bars are now required: clear the share to be a suspect, agree on a period to be convicted. The original 0.60 was chosen when only the top and bottom rows existed and the gap between them was empty; the middle two landed in that gap afterwards.

Expect to move it again. This threshold measures steadiness, not anything about a display, and the engine keeps getting steadier. Share is also noisy run to run: a second six-window set of the same subject on the same box spread 0.19-0.86 where the first spread 0.60-0.85.

The principled fix is to test the period against rates a display actually runs at - 20.97 ms is 47.7 Hz and is no display, 6.06 ms is 165 Hz and is. Deferred deliberately, not rejected.

One incidental behaviour kept on purpose: the verdict reads shapes from captures the statistics gate discarded. It looks wrong. In the run above, that discarded capture was the only thing standing between a good set and a false conviction.

05The 20.77 ms spawn was never a shipped cost

The epic's largest outstanding item, ranked at 20.77 ms across five shipped scenarios. It does not exist.

spawn_ship_skin is a no-op for every shipped ship. ShipHull::skin is false by default, both the config docs and the authoring builder say so outright ("Every shipped ship ... goes unclad"), and grep -r "skin: true" assets/ returns nothing. Measured directly: 267 calls, 1.711 ms total, mean 6.4 microseconds.

The 20.77 ms came from wfc_arena, the only clad subject in the tree. That is the sixth time this epic ranked against a cost that was not where it was believed to be, and the first where the cost was never there at all.

06Two cheap fixes the audit found instead

Landed / 7fedcf82 + 88cd968a

Every particle buffer was 16 to 1000 times too big

All three hanabi effects in the tree allocated a 32,768-particle per-instance GPU buffer. The ceiling is derivable from the burst and the lifetime, and nobody had derived it.

effectpeak neededwasnow
muzzle flash1000327682048
torpedo blast40032768512
launch puff2832768512

Verified by correctness passes on four firing ranges, all green with no truncation warnings. Not verified: any frame-time or memory win. The harness has no RSS or VRAM instrument, and the PD stress A/B came back flat - correctly, since this is a spawn-time allocation and the capture window opens long after. The reduction is arithmetic, not measurement.

Landed / dae23d00

A scenario now warms its hull art at load

Section glTFs were demand-loaded by the first ship that used them. Traced, menu_duel's parts loaded 2.7 s after the load, interleaved with the sections that needed them; final_tally's cargob never loaded at all inside the run window. Both now load beside the scenario load.

ScenarioPreload walks the config's spawn actions and holds the handles. The spawn path is untouched - AssetRef::resolve is idempotent, so the spawn asks for the same path and gets the warm handle. Ships are the only object kind naming a glTF, so the walk stops there.

Costs 11 meshes / 0.111 s on menu_duel, 17 / 0.117 s on final_tally, both settling on the same frame index as before. This buys pop-in latency, not frame time, and should never be written up as a frame-rate result.

07What is open, and what is merely unverified

The distinction matters. Unmeasured is a legitimate state; a claimed measurement that was not run is not.

Open work

  • Cracks in a mixed fleet. No section crosses bucket 1 in any current subject, so the shared-bucket handle is still argued rather than measured. Fully damaged is stock, so the only new case is mixed.
  • Velocity HUD builds twice at player spawn, 4.60 + 3.44 = 8.0 ms. An On<Add> observer building a 32,768-triangle octahedron and a fresh material per invocation, no cache. Under the panel, so latency.
  • Asteroid spawns cost 10-19 ms each in the build closure, which the spawn budget never sees - it measures the apply only. 257 ms over 28 commands.
  • NOVA OS scenes re-mint on every tab open, torn down on close. Mid-flight. The last untouched Tier 1 item.
  • Refresh-cap discriminator, second pass. Test the period against real display rates instead of using share as a proxy.

Landed but unproven

  • Particle capacities. No RSS or VRAM instrument exists. The size reduction is arithmetic; no win has been measured.
  • The glTF failure branch. The 10 s deadline is unit-tested against a handle the AssetServer never reports on. The "asset failed, warn and carry on" path is code-reviewed only - proving it needs a deliberately corrupt fixture.
  • The scenario clock now starts at 0. It used to take one tick on the load frame - 0.25 s of a long boot frame - because the queue was still empty when Update ran. Probably a fix, but it shifts every timer-gated beat.
  • Blast effect caching. broadside fires no torpedoes, so it has never been exercised. The muzzle share is confirmed; the blast share is not.
  • Release-profile numbers. Everything here is dev profile. Dev ranks, release certifies.

One stale doc found and not yet fixed. nova_probe_cli/src/evaluation/profile.rs's module doc states that an observer never gets a span of its own. In Bevy 0.19 observers do get system: spans - that is how the spawn apply was attributed. Anyone trusting that doc would conclude the observer cascade is unmeasurable.

03 / medium, protects every future number

Give the refresh-cap check a real discriminator

The share bar works today because 0.72 sits above every workload yet measured. It is a proxy for the thing actually being claimed, it is noisy (0.19-0.86 on one subject), and it will drift as the engine gets steadier.

Testing the cluster median against rates a display actually runs at tests the claim directly. Worth doing before the next cross-release comparison, not after.

04 / medium, may resolve to nothing

Price cracks in a mixed fleet

D24's open caveat. Needs a subject where sections actually cross bucket 1 - screenshot_damage_levels stands five ships at progressively worse damage through the real apply_damage path and already wires the probe.

Be honest about the odds: fully damaged is stock and pristine is v0.10.0, so the only genuinely new case is mixed, and it may price out at nothing. Census-gate it before spending the lane on timing.

What not to do next: chase the remaining spawn-time milliseconds. The apply is 0.56-1.75 ms and already inside its budget, the asteroid cost sits under a panel the player is braced for, and the epic has now ranked six times against costs that had moved. The frame-time work in this epic is finished; what is left is a release to ship.
