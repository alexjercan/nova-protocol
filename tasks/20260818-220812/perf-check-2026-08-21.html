The choice Phase A made is now the wrong one, and it should be reversed. Phase A reported the median admitted p99 because on an unbounded window the worst frame was a lottery - 46% detectable at best, against p99's 27%. On the bounded window that inverts: the worst frame detects 12% and p99 detects 20%.

The mechanism is straightforward once stated. p99 of 360 frames is the fourth-worst sample and behaves like an order statistic of a small set. The worst frame of a window that contains the same EVENT every run - here the death burst, section 06 - is a measurement of that event. Bounding the window did not merely reduce noise; it changed what the tail is a sample OF.

A single capture now detects 22%, which is better than Phase A could reach with eight.

03The clamp regime is gone

Phase A rejected fixed-timestep amplification as a CAUSE, but recorded it as a real amplifier: four of ten runs reached the 16-step ceiling and sat there at 322-354 ms a frame for up to 36 consecutive frames. That regime does not occur at all now.

A Phase B1 diagnostic reading is now false, and the check that rests on it is not. Phase B1 read the zero-step bucket as the stopped-clock tail, and justified it: the fastest frame in either affected run was 57.6 ms against a 15.625 ms timestep, so a frame could only run zero steps if the clock had stopped.

That justification is dead. Every zero-step frame in this set is 13.8 to 15.1 ms - faster than the timestep - so it is an ordinary frame that did not cross a step boundary. There are 11 to 24 of them per capture and none of them means anything is wrong.

The capture_simulated CHECK is unaffected, because it reads Time<Virtual>::is_paused() off the clock rather than inferring from the bucket table. That was the right call and it is why this correction costs nothing. The bucket table is now a workload reading only.

Read the cv columns for the tail, not just the millisecond columns. The baseline's p99 and worst frame carried cv of 59.7% and 82.2% because ONE of its eight captures entered the 16-step clamp and reported a 322.56 ms frame. Nothing in this set exceeds four steps in a frame, and the tail's dispersion falls to 5.6% and 18.7%.

The mechanism is measured elsewhere and is not in doubt. Per-step, over the saturated hold: wall median 5.81 -> 4.61 ms, contacts 1,945 -> 190, dynamic bodies 2,221 -> 340, and the worst step 17.4 -> 11.8 ms - back inside the 15.625 ms tick, which is exactly where the clamp stops being reachable. Solver constraints did not move at all (38 -> 38), confirming D20: those contacts were AABB overlap pairs from speculative margins on fast bullets that never reached the solver.

The absolutes here are floored by the instrument, so the game-side improvement is larger than -23%. Both arms carry Xvfb's per-pixel present cost, measured at about 13.7 ms at 720p (D12). Subtracting it as a constant puts the game-side frame at roughly 16.5 ms before and 9.4 ms after, which is nearer -43%. That is an INFERENCE from a constant measured in another context, not a measurement, and it is offered only so the -23% is not read as the whole story.

05b. The refusal, and what it says about this subject

Capture #3 was refused: reason=refresh_capped, 80.1% of its window within 5% of a 25.812 ms median. The run therefore FAILS capture_simulated and log_clean - twice for one cause, by design. Presentation was verified as immediate on every capture, so this is not the mode falling back.

The clustering figures across the eight tell the story: 0.140, 0.270, 0.371, 0.444, 0.446, 0.460, 0.500 and the refused 0.801. D13 calibrated this check against measured immediate captures spreading 0.03-0.44. This subject now sits at the top of that band and occasionally above it.

The reading is that the subject has nearly outgrown Xvfb as an instrument, and this is D12's lesson recurring rather than a new defect. As the game side of the frame shrinks, a fixed per-pixel present cost becomes a larger share of it, and a frame time dominated by a constant is exactly what a refresh-cap detector is built to refuse. It is right to refuse it.

Consequence for whoever measures this next: this pairing is at the end of its life. One more improvement of this size and the Xvfb arm stops being able to admit a capture at all. The successor is a real-display or headless protocol - and re-baselining is the cost of switching, which is why it was not switched inside this check.

One validity note worth keeping, because it is the property Phase A said a baseline subject needs and the 4v4 did not have. The range's own workload counters across the eight captures: 13.39-13.88 rounds a step (a 3.6% spread), trigger duty 0.719-0.745, mean aim error 5.13-5.48 degrees. The baseline set's peak live rounds spanned 934 to 2,425. This subject now measures the same workload every run, which is what D16's frame-rate invariance work bought and what makes the numbers above comparable at all.

07What this check does not answer

Recorded so nobody ranks against a cost that has moved, which is the failure this epic has now hit five times.

Open / instrument

The window is now short in GAME time, and nobody re-derived it

360 frames covered 71-101 seconds of fight when a frame cost 94 ms. At 20 ms it covers 441-514 steps, about 7-8 seconds. The bound was derived from frame counts on a five-times-slower game, and it silently shrinks as the game gets faster.

Zero refusals across eight captures validates the bound as SAFE. It does not validate it as sufficient. The plan already names this - the three frame-count windows want re-indexing to simulated time - and this check is the second piece of evidence for it.

Open / not measured

Pipeline compilation is still the only live bake candidate

synchronous_pipeline_compilation: true is unchanged and deliberate: an async compile task holding a device reference at teardown SIGSEGVs one run in five. So a first-draw shader compile is a chosen main-thread block.

It is not measured in this tree. D19 could not see it - there is no render sub-app headless - and the arena's capture opens 11.6 s in, by which time first draws are done. The 68.09 ms figure it was ranked on is old and belongs to a different tree.

Not measured

The 60 FPS line was not re-taken

D11's target is a 1v1 at 60 FPS, and its reference is the frozen wfc_ships gallery: empty 3.02 ms, one hull 27.60, two 34.82, three 44.04, on a real display. Nothing in this check re-measured it.

The gallery is a static scene, so neither the fixed-loop executor nor swept rounds should touch it - but "should not" is not a measurement, and the standing rule is that a number that did not move gets reported as a number that did not move. It is unreported here, not unchanged.
