All three are one bug. "One asset per instance where one asset would do." A distinct asset is extracted, prepared, bound and written every frame no matter how many entities share its value -- so duplicating an asset costs real time, while duplicating an instance of a shared asset is nearly free.

This was later confirmed as the shape of the whole curve: the frame tracks distinct mesh assets, not instances -- R2 0.996 against 0.910, with marginal per-instance cost drifting 4.9x across the sweep while per-distinct-mesh drifted 1.58x. hull-01.glb is one mesh drawn 136 times and costs almost nothing.

02What we believed and had to retract

Five retractions. Four were the measuring apparatus reporting a plausible number that belonged to something other than the game. This is the most useful section on the page, because the failure mode repeats.

ClaimWhat was actually trueRoot cause
"An empty scene costs 16.74 ms." Written into the release's definition of done as a hard precondition on 60 FPS. 3.02 ms. The other 13.7 ms was the display server. Measuring under xvfb-run. A software X server has no scanout, so presenting is a CPU copy of every window pixel. Additive and per-pixel, so every ratio survived and every absolute died.
"One capture read 16.67 ms because of a 60 Hz composited path." There is no compositor on this host and the output is 165 Hz. 60 Hz was never its refresh. WinitSettings::game() sets unfocused_mode: reactive_low_power(1/60). Its own comment claimed the opposite. Any capture off the focused workspace read the event loop's number.
"Prepare + PrepareMeshes is 16.1 ms of a 26 ms frame." This was the stated target for a whole lane. Prepare 13.66, PrepareAssets 4.30, PrepareMeshes 0.30 -- 1.3%, noise. PrepareAssets chains outside the top-level chain, so its time was attributed to a neighbour.
"The cladding key space is 58, so tiles never share a mesh." One hull touches 10 distinct shapes. Two hulls share all ten and add one. SkinAssets works exactly as documented. Reasoning from the size of a type's domain without checking how much of it gets used.
"Sections author a density, and the shipped hulls are 660x too heavy." The field read as mass was health. Density is a hardcoded 1.0 and mass is volume. Misreading a positional argument in a builder signature, then building an entire narrative on it before checking.

The response was to make the instrument refuse rather than warn. Four named aborts now exist -- ABORT_SIMULATION_STOPPED, ABORT_WINDOW_SIZE, ABORT_UPDATE_THROTTLED, ABORT_REFRESH_CAPPED -- because in every case above the wrong number was plausible, and a plausible wrong number survives review.

04The unexamined

Ranked by my guess at payoff times cheapness. Each says why it might matter and how to find out without a project. Nothing here has been measured -- that is the point of the section.

01 / strongest lead

An empty scene has 433 observers and 586 archetypes

Those counts are from a scene with zero meshes. Bevy dispatches observers per trigger, and query iteration cost scales with the number of matching archetypes, not just entities. A WFC hull adds sections with many optional component combinations -- exactly the shape that fragments archetypes.

If a hull takes 586 archetypes to 2,000, every system in the schedule gets slower at once, and it would look like "everything is a bit slow" rather than like one hot system. That is precisely the profile we have been unable to attribute.

How to check The census already counts archetypes. Add ship count as the sweep axis and see whether archetypes grow linearly with hulls. One run.

02 / a smell with a number on it

The Shadow phase costs 0.64 ms of CPU and produces no GPU pass

That is CPU work whose output nobody consumes. The likely mechanism: a shadow-casting directional light makes bevy cull every entity against each cascade view. Four cascades means four extra visibility passes over every entity in the scene, on top of the camera's own.

The earlier ruling "shadow maps: 0.000 ms" read the GPU side only and is not wrong so much as half an answer. The CPU side was never looked at.

How to check Turn shadows off on the scenario's one caster and re-measure. The flag already exists in the light config.

03 / I ruled this out without looking

The protected 2.00 ms per ship was never broken down

"Everything not drawn" -- physics, colliders, AI, health, integrity -- measures 2.00 ms a ship and was set aside because the epic protects gameplay logic from being traded for frames. That rule forbids trading it. It does not forbid measuring it.

If 1.8 of those 2.0 ms turn out to be one carelessly written system rather than the physics solver, fixing it costs nothing and breaks no rule. At 42% of a ship it is the largest single unexamined block in the game, and I excluded it from scope on a category error.

How to check framecost already reports every main-world schedule. Read the existing captures -- the data may already be on disk.

04 / the same bug, elsewhere

Six more sites mint assets per entity or per loop iteration

All three landed wins were "one asset per instance where one would do". A grep for the pattern finds it still living in: nova_os_ui/src/ship/scene.rs:268 (inside a for view in &views loop), nova_os_ui/src/map/scene.rs:81 (inside a .map), nova_hud/src/lib.rs:773, maneuver_instruments.rs:316, velocity.rs:473 and :567.

Some are spawn-time singletons and harmless. The NOVA OS ones run while the game is frozen, so they cost a stutter on open rather than frame rate. Worth an hour to classify, not a project.

How to check Read six call sites and ask "how many entities reach this line".

05 / strategic, and cheap to settle

Is the GPU doing anything at all?

On the empty scene the entire GPU cost is 0.312 ms of a 3.02 ms frame -- about 10%, with bloom the largest item at 0.122 ms. If that ratio roughly holds once hulls are on screen, then the GPU is idle and every shader, material and overdraw idea is misdirected. The whole game is CPU-bound in the render world's preparation stage.

We have never stated this as a conclusion, and it would redirect the entire remaining effort if true. It also predicts that resolution scaling will keep looking useless, which matches what the resolution sweep found.

How to check One NOVA_PERF_RENDER_DIAG capture at one and three hulls. Compare GPU total against frame total.

06 / never measured, at all

Audio, transform propagation, and UI layout

Audio has not been measured once this epic. Spatial mixing runs per emitter and a fight has many.

Transform propagation walks a deep hierarchy: ship -> section -> render child -> plates -> greebles. Propagation cost is sensitive to depth, not only to count, and WFC hulls are the deepest thing in the game.

UI layout: PostUpdate is 0.705 ms of a 1.77 ms main world on an empty scene, and it is the largest main-world block there. The scene has 161 HUD nodes of which 113 carry Text. Text shaping and taffy layout are not free.

How to check framecost reports schedules already; the question is which systems inside PostUpdate. One traced pass.

07 / the owner found this one by playing

What does a projectile introduce?

The point-defence case fields roughly 2,000 rounds. Nobody has counted what a single round contributes in distinct assets -- mesh, material, trail, particle effect. Given that the frame demonstrably tracks distinct assets, and given that pointing the camera at the torpedoes measurably costs frame time, this is the one place where the established law and an observed symptom meet and nobody has looked.

How to check Census by origin on the stress case, camera on the lanes versus camera away. In flight now.

08 / grows over a match, invisible in a capture

Anything that accumulates

Every measurement in this epic is a few hundred frames of a scene in a fixed state. Nothing has measured a long match. Candidates that grow and are never reclaimed: wreck bodies (the rationing that used to cap them was deleted with the slicer and never replaced), dead assets lingering in Assets<T> where prepare_erased_assets still iterates them, and event backlogs.

A capture that opens 90 frames after Playing cannot see any of this by construction.

How to check One long arena run with a census at start and at five minutes. Compare the counts, not the milliseconds.

09 / a whole platform

Nobody has measured wasm

nova_perf_web exists and the harness accepts ?perf as its arm. The wasm build was dead on load until a fix this cycle, and since it came back nobody has recorded a single frame time. Browser performance is not predictable from native -- different allocator, no threads by default, a different GPU path.

How to check Load the build with ?perf and read what falls out.

05What I chose to ignore, and whether that was right

Right to skip

  • LoD. Closed wontdo. Every axis it attacks was measured not to bind, and the one real win in its candidate list is captured more cheaply as a static reduction.
  • Ablation switches. Superseded rather than skipped -- direct per-phase attribution answered the same questions with no throwaway branch and no risk of a knob silently ablating nothing.
  • Surface-not-volume meshing. Closed: it could not buy a frame.
  • The editor. Out of scope for this release by an explicit decision.

Should be revisited

  • The protected 2.00 ms. Excluded from measurement when only trading it was forbidden. See card 03.
  • The 4v4 never got a clean post-fix number. Deferred once deliberately, then the tree kept moving underneath it. It is the epic's named benchmark and it currently has no trustworthy figure.
  • Bake-at-load and preload are untouched. Both fix stutter rather than steady state, so the demotion was right, but neither has been looked at since.
  • Wreck rationing is on hold by owner decision and is the only known unbounded growth in the game. See card 08.

06The one number that decides what happens next

The harness now reports a single hull at 5.44 ms mean, 3.02 ms min, where the same scene measured 28.41 ms earlier the same day. That move is larger than the sum of the fixes that can account for it, and it disagrees with the owner's own hand-run of 36-48 FPS.

If it is true, 1v1 is already inside the 60 FPS budget and the performance thread can close. If it is not, the harness has drifted from the game for a sixth time. The hand-run is the instrument that has been right every time this epic has disagreed with itself -- it is what caught the display-server error -- so that reading, not another capture, is what settles it.
